### 关键决定

1. **先下载再播放**，不改流式解码——复用已验证的 Player，代价是首次 1–4s。
2. **播放器不知道"远程"**：所有远程逻辑止步于命令层。
3. **能不用加密就不用**：网易云明文接口可用，省掉 500 行 AES/RSA 与三个依赖。
4. **序号跨源连续**，`play <n>` 无歧义。

### 已知限制

1. **远程曲目无封面**（网易云老接口无 `picUrl`；B 站图需带 Referer 下载，另卡）
2. **B 站结果相关性差**：混入大量直播切片，未按播放量/时长重排
3. 缓存根在 `appdata/streams` 而非 OS cache 目录
4. 退出时后台下载线程不取消（半截 `.part` 由下次清理）
5. 搜索最坏 1–2s（串行 + 300ms 节流，刻意不并发以免风控）

## 17. T-0047 完成：按艺人检索（2026-11-11）

**探测结论（真实接口）**

三种查询的 `author == 明前奶绿` 命中都是 **0**——B 站没有"艺人"字段，只有上传者和标题，因此旧的"按上传者过滤"结构性必然为 0。

| 查询 | 标题命中 artist | 其中同时含歌名 |
|---|---:|---:|
| `不为谁而作的歌 明前奶绿` | 63 | 10 |
| `明前奶绿 不为谁而作的歌` | 69 | **16** |

**最终规则**

- `--artist` 语义 = "这个人的名字"：B 站匹配**上传者或标题**，Author 优先排序；网易云仍按结构化 `artists`。
- **同时给关键词与 artist 时，B 站要求标题也含关键词**（精度规则：69 → 16）。
- 查询拼法用 `艺人 关键词`（召回最高），带 artist 时候选池 `min(limit*3, 50)`。

**真机验证**

```
search 不为谁而作的歌 --artist 明前奶绿 --source bilibili
→ 15 条，全部是"明前奶绿 + 不为谁而作的歌"的切片，907ms
```

**已知取舍**：标题子串匹配可能误杀"歌名被拆开/改字"的视频；只给 `--artist` 时仍会带出"提到这个人"的无关视频（符合"只想看这个人"的语义）。
