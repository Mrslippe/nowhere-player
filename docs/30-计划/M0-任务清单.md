## 三、终端双方案对比（本里程碑的核心决策）

### 3.1 为什么并行做两套

上一版方案直接排除了 xterm.js，理由是它的字符网格限制了排版表现力。但"看起来更自由"不等于"实际更好看"——xterm 的**真实感**（等宽对齐、光标、滚动惯性）也可能是我们想要的那部分。既然只有两天成本，就两套都做，看完再定。

### 3.2 怎么保证"可比"

两套渲染器**共用同一个输出模型**（ARCH-005），只替换渲染层：

```
命令层（mock 数据）→ Block/Output 模型 → ┬─▶ 结构化渲染器（React 组件）
                                        └─▶ xterm 渲染器（模型 → ANSI 序列）
```

这样比较的是"呈现方式"，而不是"两套功能"。切换用 URL 参数（`/terminal?variant=xterm`）或 dev 面板，不写两套命令逻辑。

### 3.3 评分维度与权重

| # | 维度 | 权重 | 怎么测 |
|---|---|---|---|
| 1 | 视觉完成度 | 30% | 同一份数据下的截图对比：表格可读性、层次、留白 |
| 2 | 交互体验 | 25% | 选区复制、滚动、补全弹层定位、长文本换行 |
| 3 | 输入法（IME） | 20% | 中文组合输入、候选框位置、拼音上屏 |
| 4 | 性能 | 15% | 1 万行回滚的滚动帧率、内存增量 |
| 5 | 后续扩展成本 | 10% | 加"可点击结果项/封面缩略图"要改多少 |

**打分方式**：每项 1–5 分，加权求和，附截图与原始数据。**不追求精确，追求可解释**。

### 3.4 决策规则

- 总分差距 ≥ 15% → 直接采用高分方案。
- 差距 < 15% → 选**长期成本更低**的那个（大概率是结构化，因为富输出不用二次开发）。
- 无论选哪个，另一套的代码保留在仓库里（用 feature flag 关闭），不删除——三个月后可能要回头看。

**决策产出**：`docs/20-架构/adr/ADR-0002-终端渲染方案.md`。

## 四、M0 完成定义

1. `git clone` 后按 README 三步能跑起来（安装依赖 → `tauri dev` → 看到两个窗口）。
2. 播放器小窗 6 种状态可切换，视觉达到设计稿要求。
3. 终端两种渲染器可一键切换，同一份 mock 数据呈现一致的信息。
4. 对比评分表与截图归档在 `docs/30-计划/` 下。
5. CI 三平台（至少 Windows + Ubuntu）构建通过。
6. 托盘、单实例、自启可用。
7. **管线验证结论**：记录本次 M0 中出现的返工、歧义、越界，写进本文件 §5。
