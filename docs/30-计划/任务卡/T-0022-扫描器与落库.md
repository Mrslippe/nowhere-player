## 1. 背景

M3 的目标是让"本地文件夹"真正可用。这一卡做**最底层**：遍历目录、读标签、写入 SQLite。不做命令、不做 UI。

## 2. 目标

`crates/np-library` 从空壳变成可用库：

1. `Database`：打开/迁移（`user_version`）、`PRAGMA foreign_keys`、WAL。
2. `Scanner`：递归遍历 → 读标签（lofty）→ 提取封面 → 归一化（artists/albums）→ 单线程写库。
3. 增量：`(size, mtime)` 未变则跳过解析，只刷新 `last_seen_at`。
4. 进度与取消：`ScanObserver` trait（`on_progress(scanned, total, current_path)`、`is_cancelled()`）。
5. 查询接口按 ARCH-003 §5 实现前四项（`search` / `list_recent` / `stats` / `tracks_by_album`）。

## 3. 非目标

- 不做命令层与 IPC（T-0023）。
- 不做封面缓存文件写入（T-0024）——本卡只把内嵌图**哈希**并写入 `cover_key`，不落盘。
- 不做 FTS5。
- 不做缺失曲目的展示策略。

## 4. 必读 / 必须核实

1. `docs/20-架构/数据模型.md`（**契约，逐表照做**）
2. `crates/np-library/src/lib.rs`（当前空壳）
3. **核实**：`lofty` 当前版本对 WAV/FLAC/MP3 的标签读取 API；`rusqlite` 的 `bundled` feature 在本机能否编译

## 6. 实施要求

### 6.1 模块结构

```
src/
├─ lib.rs        # 对外 API：Database / Scanner / Track / ScanObserver
├─ schema.rs     # DDL + migrations（user_version 1）
├─ db.rs         # 连接管理、PRAGMA、事务辅助
├─ scan.rs       # 遍历 + 并行解析 + 单线程写入
├─ metadata.rs   # lofty 读取 + 封面哈希
├─ repo.rs       # upsert / 查询
└─ error.rs      # LibraryError
```

`lib.rs` ≤ 120 行。

### 6.2 关键约束

- **写库单线程**：解析结果通过 channel 汇入 writer 线程，禁止多线程各自 `Connection`。
- **事务**：每 200 条或扫描结束提交一次；单条失败不回滚整批（用 SAVEPOINT 或逐条提交 + 错误计数）。
- **封面哈希**：对原始字节做哈希（`sha2` 不在允许清单，用 `std::hash` 的稳定变体或简单的 FNV-1a 64 位）取 hex 前 16 位；**本卡只写 key，不写文件**。
- **归一化顺序**：`artists`（按 name 去重）→ `albums`（按 title+album_artist）→ `tracks` → `track_artists`。
- **缺失判定**：扫描开始时记 `scan_started_at`；结束时把 `last_seen_at < scan_started_at` 的记录数统计出来（**不删**）。
- **取消**：`is_cancelled()` 返回 true 时，停止遍历、**提交已解析的部分**、返回 `Cancelled` 状态。

### 6.3 对外 API（建议形状）

```
Database::open(path) -> Result<Database>
Database::migrate() -> Result<u32>            // 返回当前 user_version
Scanner::new(&db, observer).scan(roots) -> Result<ScanReport>
ScanReport { scanned, indexed, skipped, failed, missing, cancelled }
search(keyword, limit) -> Vec<Track>
stats() -> Stats
```

`Track` 要能 `serde` 序列化（后续命令层直接复用）。

## 7. 验收标准

- [ ] `cargo test -p np-library` 通过，≥ 15 个用例：
  - 迁移：空库 → `user_version == 1`；重复迁移幂等
  - 扫描：临时目录放 3 个 WAV → 3 条 track；重复扫描不产生重复
  - 增量：修改一个文件 mtime → 只有它被重新解析（用 observer 计数断言）
  - 缺失：删掉一个文件再扫 → 该行仍在，`last_seen_at` 未更新
  - 归一化：两首歌同专辑 → 只有一条 album；同艺人不同大小写 → 只有一条 artist
  - 失败：放一个损坏文件 → 该文件记失败，其余正常入库
  - 取消：observer 在第一个文件后返回 true → 结果 `cancelled`，已入库部分保留
  - 查询：`search` 命中标题/艺人/专辑；`stats` 数字正确
- [ ] `cargo clippy -p np-library --all-targets -- -D warnings` 零警告
- [ ] `cargo fmt --all -- --check` 通过
- [ ] 只新增允许的五个依赖
- [ ] `lib.rs` ≤ 120 行

## 8. 测试要求

- 测试自己生成 WAV（用 `np-audio` 的 `make_wav` 思路或直接写 PCM 头），**不要往仓库塞二进制**。
- 数据库一律用临时目录，测试结束清理。
- 时间相关断言不要依赖真实时钟间隔（用 `mtime` 显式设置）。

## 11. 风险

- `rusqlite` 的 `bundled` 首次编译要几分钟（编译 SQLite 源码），属正常。
- WAV 文件通常没有标签，`title` 走文件名兜底——测试要接受这一点，不要为"标签解析"造 FLAC。
- 并行 + 单线程写入的 channel 容量要有限（如 64），否则大库会吃内存。
- 封面哈希不要用随机化哈希器（`DefaultHasher` 每次进程种子不同），否则同一图片会算出不同 key。**用 FNV-1a 或 sha2 这类确定性算法**。
