## 0. 事实基线

- `only_audio=1` 与普通 FLV 音频偏移实测 0.0s，不是流源本身更慢。
- B1.1 启动 drain 把混音自相关从约 1.96s 降到约 0.13s，但用户仍听到 1–2s；运行期缓冲仍不可控。
- 当前链路：`FlvAdtsSource → MediaSourceStream(64KB) → AdtsReader → Player ring(150ms)`。
- 社区方案参考：B站追帧脚本 `buffer = buffered.end - currentTime`，默认目标 1.5s；mpegts.js `liveBufferLatencyChasing` / `liveSync` 用 playbackRate。
- 我们无 MSE `currentTime`，也不能直接改 PCM 速率（会变调）；B1.2 用**直接 AAC 解码 + 有界帧队列 + 丢旧帧**。

## 0.1 B1.2a 结果（2026-11-17）

- direct `AacDecoder` + raw frame 队列可行，10s 解码 0 errors。
- 300ms 目标失败：10s 只输出 4.0s PCM，drop 7.5s、underrun 5.9s；CDN 约 1s 块突发，300ms 队列无法覆盖。
- no-drop 诊断：10.0s PCM、0 errors、0 underrun，平均 buffer **884ms**、最大 **1388ms**。
- 因此目标先调整为 **900ms / max 1400ms / min 500ms**；B1.2c 因真机断音再升到 **1000 / 1500 / 800**。300ms 不再作为产品目标。
- 证据：`spikes/bili-live/b12a_measurements.jsonl`，提交 `e38f6c1`。

## 0.2 B1.2b 真机结果（2026-11-17）

- direct queue 已接入 `np-live`，B1 的 only_audio/独占/Esc/队列/150ms ring 保留。
- 启动 3.0s 出现 `LIVE 661ms`；30s `491ms`；5min `470ms`，未持续增长。
- 5min 进程存活，内存约 22.8 MB，CPU 总计约 5.4s；Esc 2s 内恢复 `未播放`。
- 低于 500ms 时增加“等待队列回填”，避免继续消费到 171ms；这会让 decode 线程短暂停等。
- `cargo check.ps1` 全通过；815 tests；T3 通过。
- 目标 900ms 是上限设计值，实际稳定在 470–660ms；但真机仍有间歇断音。

## 0.3 B1.2c 稳定性修正（2026-11-17）

- 断音原因：实际 buffer 470–660ms，CDN 约 1s 空窗会打穿 500ms 下限；低于 500 后只等回 500，没有余量。
- 固定策略改为 **target 1000 / max 1500 / min 800**；低于 800 时等待回填到 1000，最多等 500ms；超 1500 丢到 1000。
- 150ms ring、only_audio、独占、Esc、队列语义不变。
- 真机 5s `LIVE 789ms`；90s `789ms`；5min `1472ms`，仍在 1500 上限内但未稳定在 1000ms。
- 5min 进程存活（wrapped `NP_TUI_LAUNCHED=1`），约 23.3 MB / CPU 5.4s；先前无 wrapper 的 app/终端会一起消失，需区分终端关闭与进程崩溃。

## 0.4 B1.2d 2000ms 断音诊断（2026-11-17）

- 用户实测 1000/1500 仍有断音；按要求直接调到 **target 2000 / max 2500 / min 1800**。
- 启动等待 target 2000，`STARTUP_TIMEOUT` 3s；仍保留 only_audio、150ms ring、Esc、队列。
- 本次是诊断阈值，不是最终低延迟结论；如果 2000ms 仍断，问题不在 buffer 深度。
- 发布 `target/release/np-tui.exe` 供真机测试；5min 数据待补。

## 1. 目标

- 直播本地缓冲目标 **2000ms**，上限 **2500ms**，下限 **1800ms**（B1.2d 诊断）。
- 超上限：在 AAC 帧边界丢弃旧帧，追到 2000ms。
- 低于下限：等待回填到 2000ms；超时才补静音。
- 启动：只保留约 2000ms 新音频，不把 CDN 初始 GOP 全部播放。
- 暂停/恢复：暂停时停止消费，恢复时重新解析 playurl 接 live edge（B1.2c）。
- 不做 time-stretch；不做 HLS；不做视频。

## 2. B1.2a 先做 spike

只改 `spikes/bili-live/**`，验证：

1. `symphonia_codec_aac::AacDecoder` 能否直接吃 raw AAC + ASC extra data；
2. 自定义 `AacFrame { pts_ms, raw }` 有界队列；
3. 900ms target / 1400ms max / 500ms min 的丢帧控制器；
4. 10s 连续解码、首帧延迟、最大/平均 buffer、drop 次数、decode errors；
5. 与现有 `AdtsReader` 路径对比 PCM/RMS/延迟；
6. 如果直解不可行，明确失败点，B1.2b 停止。

## 3. B1.2b 产品实现

- `np-live`：网络线程 → FLV tag → `AacFrame` 队列；解码线程用 `AacDecoder` 直接解。
- 保留 `only_audio=1`；视频 tag 只丢弃。
- `TuiAudio`：暴露 `buffer_ms`（可进状态栏）；直播仍 150ms ring。
- 暂停恢复接 live edge；不保留旧缓冲。
- 不引入新第三方依赖；`symphonia` 已在 workspace。

## 5. 验收

### B1.2a

- 直解 10s：`decode_errors=0`，PCM 非静音；
- 队列 buffer 可计算，drop 只在 >1500ms 触发；
- 首帧 PCM 延迟记录。

### B1.2b T3

- app 端到端约 **1.0–1.2s**，比浏览器默认 1.5s 低 **≥300ms**；用系统混音自相关/loopback 记录；
- 连续 5 分钟 buffer 不持续增长；
- drop 次数、underrun 次数可记录；
- 启动 3s 内出声；
- `Esc` 停止、队列保留、next/prev/seek 禁用不回退。

## 6. 停止条件

- 直接 AAC 解码 API 不可用；
- 需要新原生依赖/FFmpeg；
- 5 分钟内 buffer 持续增长或不可闻；
- 需要改 `np-core`/`np-app` 契约。
