## 0. 事实基线

- `only_audio=1` 与普通 FLV 音频偏移实测 0.0s，不是流源本身更慢。
- B1.1 启动 drain 把混音自相关从约 1.96s 降到约 0.13s，但用户仍听到 1–2s；运行期缓冲仍不可控。
- 当前链路：`FlvAdtsSource → MediaSourceStream(64KB) → AdtsReader → Player ring(150ms)`。
- 社区方案参考：B站追帧脚本 `buffer = buffered.end - currentTime`，默认目标 1.5s；mpegts.js `liveBufferLatencyChasing` / `liveSync` 用 playbackRate。
- 我们无 MSE `currentTime`，也不能直接改 PCM 速率（会变调）；B1.2 用**直接 AAC 解码 + 有界帧队列 + 丢旧帧**。

## 0.1 B1.2a 结果（2026-11-17）

- direct `AacDecoder` + raw frame 队列可行，10s 解码 0 errors。
- 300ms 目标失败：10s 只输出 4.0s PCM，drop 7.5s、underrun 5.9s；CDN 约 1s 块突发，300ms 队列无法覆盖。
- no-drop 诊断：10.0s PCM、0 errors、0 underrun，平均 buffer **884ms**、最大 **1388ms**。
- 因此目标先调整为 **900ms / max 1400ms / min 500ms**；B1.2c 因真机断音再升到 **1000 / 1500 / 800**。300ms 不再作为产品目标。
- 证据：`spikes/bili-live/b12a_measurements.jsonl`，提交 `e38f6c1`。

## 0.2 B1.2b 真机结果（2026-11-17）

- direct queue 已接入 `np-live`，B1 的 only_audio/独占/Esc/队列/150ms ring 保留。
- 启动 3.0s 出现 `LIVE 661ms`；30s `491ms`；5min `470ms`，未持续增长。
- 5min 进程存活，内存约 22.8 MB，CPU 总计约 5.4s；Esc 2s 内恢复 `未播放`。
- 低于 500ms 时增加“等待队列回填”，避免继续消费到 171ms；这会让 decode 线程短暂停等。
- `cargo check.ps1` 全通过；815 tests；T3 通过。
- 目标 900ms 是上限设计值，实际稳定在 470–660ms；但真机仍有间歇断音。

## 0.3 B1.2c 稳定性修正（2026-11-17）

- 断音原因：实际 buffer 470–660ms，CDN 约 1s 空窗会打穿 500ms 下限；低于 500 后只等回 500，没有余量。
- 固定策略改为 **target 1000 / max 1500 / min 800**；低于 800 时等待回填到 1000，最多等 500ms；超 1500 丢到 1000。
- 150ms ring、only_audio、独占、Esc、队列语义不变。
- 真机 5s `LIVE 789ms`；90s `789ms`；5min `1472ms`，仍在 1500 上限内但未稳定在 1000ms。
- 5min 进程存活（wrapped `NP_TUI_LAUNCHED=1`），约 23.3 MB / CPU 5.4s；先前无 wrapper 的 app/终端会一起消失，需区分终端关闭与进程崩溃。

## 0.4 B1.2d 2000ms 断音诊断（2026-11-17）

- 用户实测 1000/1500 仍有断音；按要求直接调到 **target 2000 / max 2500 / min 1800**。
- 启动等待 target 2000，`STARTUP_TIMEOUT` 3s；仍保留 only_audio、150ms ring、Esc、队列。
- 本次是诊断阈值，不是最终低延迟结论；如果 2000ms 仍断，问题不在 buffer 深度。
- 发布 `target/release/np-tui.exe` 供真机测试；5min 数据待补。

## 0.5 B1.2e 诊断计数器（2026-11-17）

用户实测 2000ms 仍断音，暂停继续加 buffer，先加可观测性：

- `LIVE` 标签格式：`LIVE 2000ms U:0 Q:0 R:0 D:0 E:0 F:0 S:0`
- `U`：队列饥饿/补静音段数；
- `Q`：`queue.pop()` 空但流未结束的次数；
- `R`：cpal ring underrun 次数（`Player::underruns`）；
- `D`：丢旧帧事件数；
- `E`：AAC 解码错误数；
- `F`：累计补静音毫秒；
- `S`：单次 `next_frame` 最长墙钟耗时（含阻塞 HTTP read）。
- `LiveMetrics` 另存 `min/max buffer`，暂不放进标签。
- 诊断判读：`U/Q` 增长且 buffer 低 → 队列/网络；`R` 增长 → ring；`E` 增长 → 解码；`D` 增长 → 丢帧；`S` 大 → HTTP read 停顿。

## 0.6 B1.2e 诊断结果（2026-11-17）

5min 实测标签：

```text
LIVE 1813ms U:0 Q:0 R:145 D:2 E:0 F:0 S:777
```

启动 10s 时 `R:29`，30s 仍为 29，5min 涨到 **145**；`U/Q/F` 全为 0，`E=0`，`D=2`。

结论：**断音不是队列饥饿，也不是 AAC 解码错误，而是 cpal ring underrun**。  
最可疑点：`read_frames` 在 `buffer < 1800ms` 时调用 `wait_span(2000ms, 500ms)`，把 decode 线程停住；此时 150ms ring 会先被 cpal 播空，`R` 增长。

换房 `25034104` 复测：

| 房间 | 10s R | 5min R | U/Q/F | D | E | S |
|---|---:|---:|---:|---:|---:|---:|
| 23197314 | 29 | 145 | 0/0/0 | 2 | 0 | 777ms |
| 25034104 | 17 | 26 | 0/0/0 | 1 | 0 | 449ms |

两房 `U/Q/F` 均为 0，说明队列和网络读取没有断流；`R` 的增量随房间/CDN 变化。23197314 的 buffer 在 1800ms 附近，触发低 buffer wait；25034104 稳定在 1942ms，R 主要是启动值。低 buffer wait 仍是首要嫌疑。

下一步（B1.2f，已实施）：移除低 buffer 时阻塞 decode 线程的等待；只在队列真正空时补静音。队列有数据时必须持续喂 ring。

## 0.7 B1.2f 修复结果（2026-11-17）

移除 `buffer < 1800` 的 `wait_span` 后，23197314 5min：

```text
LIVE 1728ms U:1 Q:2 R:0 D:1 E:0 F:42 S:1751
```

- `R:0`：cpal ring underrun 消失；
- `U:1 Q:2 F:42`：只发生一次约 42ms 的队列空窗，与 `S:1751` 的一次 1.75s CDN 读取停顿对应；
- `D:1`、`E:0`：无解码错误；
- 结论：断音主因是 decode 线程被低 buffer wait 阻塞，不是队列深度；偶发 42ms 空窗可后续再调 buffer/重连。

## 0.8 B1.2g 1500ms 稳定值（2026-11-17）

B1.2f 修复后，把 2s 诊断值降到 target 1500 / max 2000 / min 1200，23197314 复测：

```text
10s   LIVE 1558ms U:0 Q:0 R:0 D:1 E:0 F:0 S:227
5min  LIVE 1515ms U:0 Q:0 R:0 D:1 E:0 F:0 S:299
```

- `R/U/Q/F` 全为 0：没有 ring underrun、没有队列空窗；
- 5min 进程存活，约 23.2 MB / CPU 7.3s；
- 端到端约 1.5s + 150ms ring ≈ 1.65s，接近浏览器默认 1.5s；
- 不再继续降 1300，避免一次 CDN 1.5s 停顿就破防；1500 作为稳定值。

## 0.9 B1.2c 暂停/恢复重连（2026-11-18）

- 新增 `LiveState::Paused`；`is_live` 保持 true，Transport 继续禁用。
- 暂停：停声并丢弃旧 Player/tap/metrics，保留 room、标题、队列；时间位显示 `LIVE PAUSED`。
- 恢复：重新 `start_live(room)`，重新取 playurl/FLV，从 live edge 开始，不续播旧缓冲。
- `Space`/`toggle`、`PlayerApi::pause/resume/play(None)` 均走直播分支；Esc 从 Paused 可停。
- 真机：暂停 2s 显示 `LIVE PAUSED`；恢复 5s 内重新 `LIVE 853ms`，R:0；恢复时遇到一次 1.4s 读取停顿，F:63，可接受。

## 0.10 B1.2d 暂停缓存（2026-11-18，实现中）

- 暂停保留 Player；`LiveControl.paused=true`，网络线程继续读；缓存到 30s 后丢新帧。
- 恢复 `LiveControl.resume()`，source 记 `replay_until_pts`，先播缓存；播到缓存尾再恢复 1500ms 控制器。
- `F5` 手动刷新：丢弃旧 Player，重走 prepare 接 live edge。
- 队列容量扩到 4096 帧（约 87s）。
- T3 初步：暂停 1s `LIVE PAUSED 1450ms F:773 C:1 P:0`；暂停 35s 以上 cap 生效：`P:2500`，帧队列封顶 1406 帧。
- 暂停标签的毫秒值来自 FLV PTS；长时间暂停后出现 82s 这类 PTS 跳变，但实际帧数 cap 仍是 30s。F5 已真机验证可回 live edge。
- 恢复续播的听感（从暂停点开始）仍需人工确认；Space 自动化受窗口焦点影响，不作为结论。

## 0.11 B2a 自动重连（2026-11-18）

- 新增 `LiveState::Reconnecting`，播放中 EOF/错误进入退避重连；`LIVE RECONNECTING n/6`。
- 退避：1/2/5/10/20/30s，最多 6 次；每次重新 `prepare`，因此重新取 playurl。
- 网络/读取/BadStream 可重试；未开播、不支持音频、取消不重试。
- `F5` 跳过等待立即刷新；`Esc` 从 Reconnecting 取消；成功清零计数。
- 暂停中断流不自动重连，保留 Paused；恢复时失败会重新连接。
- T3：F5 已真机验证；真实断网/断流场景未模拟，自动重连仅单测覆盖状态/退避/错误分类。

## 0.12 qn 对齐浏览器（2026-11-18）

- 浏览器插件使用 `qn=10000` 普通 FLV；app 默认 `qn=80 + only_audio` 命中另一组 CDN/转码。
- 默认改为 **qn=10000 + only_audio=1**；`NP_LIVE_QN` 保留诊断覆盖，`NP_LIVE_NORMAL=1` 可走普通 FLV。
- 默认 qn10000 only_audio 真机：`LIVE 1003ms U:0 Q:0 R:0 D:0 E:0 F:0 S:1752`。
- 本地队列低于浏览器 1.5s；是否解决体感差需用户 A/B。

## 0.13 同源 URL A/B（2026-11-18）

- 使用浏览器实际 FLV URL（qn10000）直连 app：`LIVE 1088ms U:0 Q:0 R:0 D:1 E:0 F:0 S:701`。
- 系统混音自相关主峰 **0.222s**；不是 1s。
- app 匿名 API 即使请求 qn10000，返回 `current_qn=250`、host 也与登录浏览器不同；浏览器登录态拿到 qn10000。
- 结论：app 本地管线与浏览器同源时差约 0.2s；1s 体感来自 qn/CDN/登录态差异，不是 buffer 或解码。
- 诊断入口：`NP_LIVE_STREAM_URL_FILE` 读取直链；默认产品不启用。

## 1. 目标

- 直播本地缓冲目标 **1500ms**，上限 **2000ms**，下限 **1200ms**（B1.2g 稳定值）。
- 超上限：在 AAC 帧边界丢弃旧帧，追到 1500ms。
- 低于下限：只做诊断，不阻塞 decode；队列空才补静音。
- 启动：只保留约 1500ms 新音频，不把 CDN 初始 GOP 全部播放。
- 暂停/恢复：暂停时停止消费，恢复时重新解析 playurl 接 live edge（B1.2c）。
- 不做 time-stretch；不做 HLS；不做视频。

## 2. B1.2a 先做 spike

只改 `spikes/bili-live/**`，验证：

1. `symphonia_codec_aac::AacDecoder` 能否直接吃 raw AAC + ASC extra data；
2. 自定义 `AacFrame { pts_ms, raw }` 有界队列；
3. 900ms target / 1400ms max / 500ms min 的丢帧控制器；
4. 10s 连续解码、首帧延迟、最大/平均 buffer、drop 次数、decode errors；
5. 与现有 `AdtsReader` 路径对比 PCM/RMS/延迟；
6. 如果直解不可行，明确失败点，B1.2b 停止。

## 3. B1.2b 产品实现

- `np-live`：网络线程 → FLV tag → `AacFrame` 队列；解码线程用 `AacDecoder` 直接解。
- 保留 `only_audio=1`；视频 tag 只丢弃。
- `TuiAudio`：暴露 `buffer_ms`（可进状态栏）；直播仍 150ms ring。
- 暂停恢复接 live edge；不保留旧缓冲。
- 不引入新第三方依赖；`symphonia` 已在 workspace。

## 5. 验收

### B1.2a

- 直解 10s：`decode_errors=0`，PCM 非静音；
- 队列 buffer 可计算，drop 只在 >1500ms 触发；
- 首帧 PCM 延迟记录。

### B1.2b T3

- app 端到端约 **1.0–1.2s**，比浏览器默认 1.5s 低 **≥300ms**；用系统混音自相关/loopback 记录；
- 连续 5 分钟 buffer 不持续增长；
- drop 次数、underrun 次数可记录；
- 启动 3s 内出声；
- `Esc` 停止、队列保留、next/prev/seek 禁用不回退。

## 6. 停止条件

- 直接 AAC 解码 API 不可用；
- 需要新原生依赖/FFmpeg；
- 5 分钟内 buffer 持续增长或不可闻；
- 需要改 `np-core`/`np-app` 契约。
