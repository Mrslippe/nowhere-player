---

## 1. 现象（产品原话）

```
search 不为谁而作的歌 --artist 明前奶绿 --source bilibili
→ 0 条
```

但该 UP 确实发过这首翻唱。

## 2. 根因

现在的 `--artist` 是**后置过滤**：先按关键词取 10 条，再筛艺人。

B 站对"不为谁而作的歌"按热度返回，那个 UP 的翻唱不在前 10——**艺人名没有参与检索**，所以必然被过滤光。

## 3. 目标（三层，逐层兜底）

### 3.1 第一层：艺人名拼进查询

给了 `--artist` 时，发给源的 query 变成 `<关键词> <艺人>`（关键词为空时只用艺人）。

### 3.2 第二层：扩大候选池

带 `--artist` 时每源抓 `min(limit*3, 50)` 条（而不是 10），再过滤、再截断。

### 3.3 第三层：纯关键词兜底

第一层过滤后为空、且关键词非空 → 用**纯关键词**再抓一次（同样放大池），再过滤。
命中则用；仍空 → 报「过滤前 N 条，被 --artist 过滤掉了 M 条」。

## 4. 必须先探测（写进回报第一段）

**"拼进去"不一定有效。** 先手工请求三种查询，看那个 UP 的翻唱有没有出现在结果里：

| 查询 | 目的 |
|---|---|
| `不为谁而作的歌` | 基线 |
| `不为谁而作的歌 明前奶绿` | 第一层假设 |
| `明前奶绿 不为谁而作的歌` | 词序是否影响 |

- 若三种都拿不到 → **停下来报告**，改走"先搜 UP 的 mid，再列该 UP 的视频"（B 站有 `space/wbi/arc/search`），那是完全不同的实现。
- 若某种有效 → 用有效的那种词序，写进代码注释说明原因。

## 5. 非目标

- 不做 `--up` / `--mid` 参数（若探测需要，另开卡）。
- 不改网易云的检索策略（它的搜索对艺人名本来敏感）。
- 不改默认 20 条与配额规则。

## 8. 测试要求

- 全部离线，用假 `AudioSource` 断言"发了什么查询、发了几次"。
- 夹具补一份"关键词+艺人"命中的样本。

## 9. 文档影响

- 回报中给出：三种查询的实际效果、最终采用的拼法、请求次数与延迟变化。
- 主线据此更新 `命令表` 的 `--artist` 语义（从"后置过滤"改为"参与检索 + 过滤"）。

## 10. 回报格式

四段式；第一段必须是探测结论。

## 11. 风险

- **请求次数会涨**：B 站本来就要发两次（duration 两个桶），带 artist 再翻倍，最坏 4 次 ≈ 1.2–1.5s。要在回报里给实测延迟；超过 2 秒要考虑缓存或减少桶。
- **拼查询可能让结果变差**：有些源对长 query 分词差，反而搜不到。所以第三层兜底必须有。
- 过滤是大小写不敏感的**子串**匹配，`明前奶绿` 与 `明前奶绿Official` 都能命中——这是想要的。
- 别把"过滤前 N 条"的 N 写错：三层兜底下 N 是最后一次抓取的数量。
