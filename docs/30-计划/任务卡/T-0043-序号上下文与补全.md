## 1. 背景（产品原话）

1. 「搜索结果出来之后，使用 `play index` 会直接播放当前播放列表中的歌曲而不是搜索结果」
2. 「`queue add [index/path]` 太宽泛了，`queue add 1` 会把路径 `1` 直接加进去」
3. 「键入指令的途中就直接显示模糊匹配候选，不用按 Tab；此时按 Tab 直接选取首个」

## 2. 目标

### A. 序号上下文：最后一张列表拥有序号

- 执行器维护一个 `active_listing`：最近一次**渲染了带序号表格**的命令决定它。
  来源：`search`、`queue list`、`library list`、`playlist show`（后者 T-0044 接）。
- `play <n>` / `queue add --from-search <n>` / `playlist add <name> <n>` 都按 `active_listing` 解析。
- 无上下文时 `play 1` → `E_CMD_ARG`「先执行 search / queue list 等命令，再用序号」。
- **输出必须写明来源**（现在 footer 已有，保留并统一）。

### B. `queue add` 收窄

| 形式 | 行为 |
|---|---|
| `queue add <path>` | **路径必须存在且是文件**；否则 `E_CMD_ARG`「文件不存在：<path>」 |
| `queue add --from-search <n>` | 从当前搜索结果取第 n 条（本地/在线都可以） |
| 其它 | `E_CMD_ARG` |

- 不再接受"任意字符串当路径"。
- 路径含空格要能通（引号规则不变）。

### C. 内联补全

- 输入时**实时**显示候选（不按 Tab）：命令名模糊匹配，最多 5 条，当前高亮第一条。
- **Tab** → 采纳第一条候选（不关闭列表）。
- **Enter** → 执行当前输入（不采纳候选）。
- **Esc** → 关掉列表。
- 只在**命令名位置**（第一个词、且是前缀）出候选；输入参数时不出。
- 命中为空时不出列表。
- 输入法与中文不影响（命令名是 ASCII）。

## 3. 非目标

- 不做参数级补全（路径、序号）。
- 不做歌单（T-0044）。
- 不改补全的匹配算法（复用现有 `completion.ts` 的模糊匹配）。

## 6. 实施要求

### 6.1 `active_listing`

```rust
enum ListingSource { Search, Queue, Library, Playlist(String) }
struct ActiveListing { source: ListingSource, len: usize }
```

- 每次渲染带序号表格的命令结束时写入。
- `play <n>`：越界报「<来源>只有 N 条」。
- **`queue add` 成功不会改变 active_listing**（它不渲染表格）。
- 会话级，不持久化。

### 6.2 兼容性

- `play <n>` 在**没有搜索也没有队列列表**时，若队列非空——按老行为播队列？**不**。统一按 `active_listing`，没有就报错。这会让老的 `play 1`（刚启动时）失效，属于预期：**规则统一比兼容一个隐式行为重要**。

### 6.3 补全

- 复用 `completion.ts` 的 `complete(prefix)`，输入变化时（debounce ≤80ms）更新候选。
- 候选渲染复用现有 `.np-lab__completion` 结构（它已是公开的视觉件）。
- **与历史 ↑/↓ 不冲突**：历史只在列表关闭时生效。
- 输入为空时不显示候选。

## 11. 风险

- **`play` 语义变化会让老习惯失效**：以前启动后 `play 1` 是播队列，现在要先 `queue list`。**必须在错误文案里教用户怎么做**。
- `queue add` 校验收紧后，`queue add` 一个不存在的远程 URL 也会被拒——这是对的，但文案要说清"只收本地文件"。
- 补全实时刷新如果每次按键都跑，输入快时可能掉帧——debounce 必须有。
- Tab 采纳候选后**不要**立刻执行（用户可能还要改），这是常见误设计。
