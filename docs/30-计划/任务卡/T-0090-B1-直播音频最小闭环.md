## 0. 事实基线

- B0.1 已确认 `getRoomPlayInfo` 加 `only_audio=1` 后，FLV 只有音频 tag：401 audio / 0 video，约 143.6 KB/8.5s。
- B1a 已确认 `AdtsReader` 可以跑在阻塞、不可 seek 的自定义 `MediaSource` 上：10.7s PCM、0 decode errors；首帧 PCM 1.157ms（不计 connect 419ms）。
- B1a 的取消是 deadline 轮询，10s 运行后退出 869ms；单次阻塞 HTTP read 无法立即打断。
- 当前 `np-audio` 的 ring 是 300ms（`RING_MS`），淡入 12ms；B1 直播目标 ring 150ms。
- 目标入口：TUI Controller 的 `live <room>`，不是 `np-core` 命令表。
- 不做：Live 页、重连、弹幕、HLS、视频画面、入站弹幕。

---

## 1. 目标

用 `:live <room>` 播放 B 站直播声音，满足：

1. 命令发出后 3 秒内出声；
2. 连续播放 5 分钟不崩溃；
3. `Esc` 停止直播，队列不被清空；
4. 直播期间 `next/prev/seek` 禁用，不自动下一首；
5. 播放条显示 `LIVE`，不显示 `00:00 / 00:00`；
6. 网络/房间错误有可读状态，不挂 UI。

## 2. 非目标

- 断线重连、playurl 刷新（B2）
- 弹幕发送、Cookie（B3）
- Live 页、房间历史、收藏（B2）
- HLS / enhanced-FLV（B4）
- 视频解码 / 终端画面（另立项目）
- 修改 `np-core` 契约、SQLite schema、settings.json schema

## 3. 关键技术决定

### 3.1 `np-live` crate

新增 `crates/np-live/`：

```text
api.rs       getRoomPlayInfo(only_audio=1) + room get_info
flv.rs       FLV tag -> ADTS（顺序、不可 seek）
source.rs    LiveAudioSource: np_audio::AudioSource
prepare.rs   后台准备 PreparedLive
error.rs     LiveError -> 可读状态
fixtures/    B0 脱敏 live/offline/error
```

依赖：`np-audio`、`np-sources`、已有 `symphonia`、`serde`、`serde_json`、`thiserror`。不要直接依赖 `reqwest`，HTTP 走 `Transport`。

### 3.2 `Transport::open_stream`

在 `np-sources` 加：

```rust
fn open_stream(
    &self,
    url: &str,
    headers: &[(&str, &str)],
) -> Result<Box<dyn Read + Send>>;
```

- 默认 `NotImplemented`，旧测试假实现不改；
- `ReqwestTransport` 使用独立客户端/请求，不能套 15s 总超时；
- 连接超时 5s；读取不在 Transport 做无限缓冲；
- B1 不实现 `post_form`，弹幕留 B3。

### 3.3 `np-audio` 流式 source

```rust
pub fn open_source(source: Box<dyn AudioSource>) -> Result<Self, AudioError>;
pub fn open_source_with_ring(source: Box<dyn AudioSource>, ring_ms: u32)
    -> Result<Self, AudioError>;
```

```rust
trait AudioSource {
    fn is_seekable(&self) -> bool { true }
}
```

- `FileSource` 不变；
- live source：`duration_ms=None`、`is_seekable=false`；
- `Engine::seek` 对不可 seek source 返回 `AudioError::Seek`；
- 直播 `read_frames` EOF/网络错误即结束；
- `MediaSourceStream` 的 buffer 实际用默认 64KB：symphonia 0.6.1 断言 buffer 必须 >32KB 且为 2 的幂，8KB 会 panic。`FlvAdtsSource` 每次只吐一个 ADTS 帧，预读量不按 64KB 填满；该口径已按 B1 实测修正。
- 直播 ring 用 `LIVE_RING_MS = 150`，普通文件仍 300ms。

### 3.4 后台准备

`TuiAudio::start_live(room_id)`：

```text
spawn thread -> LiveClient::prepare
  -> API room/playurl
  -> open_stream
  -> FLV header + AAC ASC
  -> PreparedLive { room, format, source }
主线程 poll -> Player::open_source_with_ring(source, 150)
```

UI 线程不做网络/连接；`prepare` 失败通过状态显示。

### 3.5 TUI

- `App::run` 拦截 `live <room>`（数字房间号）；不进 `np-core` 命令表；
- `TuiAudio` 增加 `is_live`、`live_rx`、`start_live`、`poll_live`、`stop_live`；
- `event_loop` 每 tick 调 `poll_live`；
- `Action::Escape`：直播时先 `stop_live`，否则沿用原逻辑；
- `TransportAvailability` 直播时关闭 prev/next/back/forward；
- `player_bar` 直播显示 `LIVE`，进度条不按 0/0 计算；
- 直播结束/出错：停止，不调用 `queue.next()`；状态写明原因；
- 启动直播停止当前播放但不清空队列；停止直播后队列仍在。

### 3.6 取消/停止

B1 接受 B1a 的 best-effort：

- 正常网络下 `Esc` 停止应在 2 秒内完成；
- 单次阻塞 HTTP read 可能拉长退出；在报告里记录实测；
- 不做 reader 线程/取消通道（B2 若实测挂起再 redesign）。
