# T-0049 UP 空间检索（--up）

| 字段 | 值 |
|---|---|
| 卡号 | T-0049 |
| 里程碑 | M6-8 |
| 依赖 | T-0048 探测（已证明关键词搜索拿不到正主投稿） |
| 预估 | 2 天 |
| 时间预算 | 墙钟 12 小时（探测 → 实现 → 接线，三块提交） |
| 并行 | 否 |
| 负责人 | 常驻「音源 / 网络」代理 |

---

## 1. 背景（探测已确认）

```
纯关键词「最长的电影」100 条 → author == 明前奶绿：0 条
关键词+艺人 100 条        → author == 明前奶绿：0 条
```

但网页版（登录态）能搜到，且该投稿 114.5 万播放。**结论：匿名关键词搜索拿不到她的正主投稿**，任何查询构造都救不了。

唯一可靠路径：**先找 mid，再列该频道的投稿**。

## 2. 目标

新增 `--up <用户名>`（仅 B 站支持）：

```
search [关键词] --up <用户名> [--limit <n>]
```

行为：

1. `bili_user` 搜索用户名 → 取 `mid`；
2. 用 `space/wbi/arc/search?mid=<mid>&keyword=<关键词>` 拉该 UP 的投稿；
3. 有关键词 → 服务端按关键词过滤（这是关键能力）；
4. 无关键词 → 列出该 UP 最近的投稿（按发布时间降序）；
5. 结果并入统一 `SourceTrack` 流，走现有的展示/播放链路。

## 3. 必须先探测（回报第一段）

1. `bili_user` 搜 `明前奶绿` → **能否拿到 mid、是否唯一、粉丝数多少**（重名怎么处理）；
2. `space/wbi/arc/search?mid=<mid>&keyword=最长的电影` → **能否返回那条 114.5 万播放的投稿**；
3. 该接口**是否需要 wbi 签名**、匿名是否可用、单页 `ps` 上限；
4. 实测延迟。

**若第 2 条拿不到**，停下来报告——那说明匿名空间接口也不返回，方案要重定（可能要登录态，那就超出本项目范围）。

## 4. 设计要点

### 4.1 用户名 → mid 的歧义

- 优先**精确同名**；多于一个时取粉丝最多者；
- 输出的第一行写明匹配结果：`已匹配 UP：明前奶绿（mid=xxx，粉丝 12.3 万）`；
- 若同名候选 ≥2，追加一行提示：`另有 N 个同名用户；用 --mid <id> 指定`；
- **新增 `--mid <id>`** 跳过解析（给高级用户，也给重名兜底）。

### 4.2 分页

- 有 `keyword` 时：最多拉 2 页（约 60 条），够用就停；
- 无 `keyword` 时：只拉第 1 页（30 条），并在尾注写「只显示最近 30 条，可用关键词过滤」。

### 4.3 与现有参数的关系

| 组合 | 行为 |
|---|---|
| `--up` + 关键词 | 空间接口按关键词过滤（推荐用法） |
| `--up` 无关键词 | 该 UP 最近投稿 |
| `--up` + `--artist` | `E_CMD_ARG`（语义重复，二选一） |
| `--up` + `--local` | `E_CMD_ARG` |
| `--up` 且 `--source=netease` | `E_CMD_ARG`（网易云不支持） |

### 4.4 缓存

- `用户名 → mid` 的解析结果在进程内缓存 1 小时（避免重复请求）。

## 5. 非目标

- 不做 UP 的合集/收藏夹。
- 不做翻页浏览（`--up` 无关键词只看第一页）。
- 不支持网易云/yt-dlp 的同类能力。
- 不做登录态。

## 9. 文档影响

- 主线据此更新 `命令表`（新增 `--up` / `--mid`）与 ADR-0004（UP 空间检索已落地，不再是"推迟"）。

## 10. 回报格式

四段式；第一段必须是探测结论。

## 11. 风险

- **匿名空间接口可能限流或需要 wbi 签名**：先探测，别一上来写签名逻辑。
- **重名 UP 是真实问题**：`明前奶绿` 可能有多个人。**必须把匹配结果显示出来**，否则用户会以为搜错了歌。
- 空间接口分页参数与全局搜索不同（`ps`/`pn`），别照抄。
- 这条链路多了两次请求（查 mid + 列表），延迟会比普通搜索高；实测写进回报。
- 若探测发现必须登录态才能拿到，**停下来报告**，不要自行加 cookie 逻辑。
