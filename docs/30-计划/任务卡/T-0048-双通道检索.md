## 1. 反例（产品提供）

她的正主投稿 `『最长的电影』我们的开始，是很长的电影~`（114.5 万播放、2180 评论）**搜不到**；
反而搜出两条别人做的歌切。

而现在我们只发一种查询（`艺人 关键词`），它偏向"切片"，把"正主的高播放投稿"挤掉了。

**两种情况需要相反的查询**：

| 场景 | 有效查询 |
|---|---|
| 正主自己的投稿（标题含歌名） | 纯关键词（按播放量排，正主靠前） |
| 别人做的切片（标题含歌名 + 艺人名） | 艺人 + 关键词 |

## 2. 必须先验证（写在回报第一段）

用真实接口确认：

1. 纯关键词 `最长的电影` 抓 **50 条**，她的视频（`author == 明前奶绿`）**在不在里面、排第几**；
2. 若不在：换成 `最长的电影 明前奶绿`（关键词在前）看能不能召回；
3. 两种都拿不到 → **停下来报告**，说明问题不在查询构造，方案要重定。

## 3. 目标

### 3.1 双通道 + 按需触发

```
通道 A（常发）：query = 关键词
通道 B（按需）：query = 艺人 + 关键词，仅当 A 过滤后 < limit 时发
→ 按 (source, source_id) 去重合并 → 过滤 → 排序 → 截断
```

- **A 足够时不发 B**：常规搜索维持 ~0.75s。
- 只给 `--artist`（无关键词）时**只发**艺人查询。

### 3.2 过滤规则按命中类型

| 命中 | 条件 |
|---|---|
| **Author**（`artist` 字段 == 艺人名，子串） | **不要求**标题含关键词 |
| **Title**（标题含艺人名） | **必须**同时含关键词（大小写不敏感） |
| 都不命中 | 丢弃 |

> 这条同时解决"误杀正主（标题没写歌名）"与"收录无关八卦"。

### 3.3 `--artist` 单独使用时按热度排

只给 `--artist`、不给关键词时，结果按**播放量降序**（B 站 `play` 字段），让它更像"看这个人的热门"。
其它情况保持既有排序（Author 优先、同档保持源顺序）。

需要给 `SourceTrack` 增加可选字段：

```rust
pub play_count: Option<u64>,   // #[serde(default)]，B 站填 stat.view，网易云为 None
```

## 4. 非目标

- **不做 UP 主空间检索**（`space/wbi/arc/search`）。标题里没有歌名的投稿**搜不到就是搜不到**，这是已知且已接受的限制；用户可用 `--artist` 单独查看这个人的视频。
- 不做并发请求（保持串行 + 300ms 节流，避免风控）。
- 不做搜索结果缓存。

## 10. 风险

- **A 的结果"够 limit"不等于"够相关"**：如果 A 返回 20 条全是不相关的，就不会触发 B。判据建议用"**过滤后**的条数 < limit"而不是"原始条数"。
- `play` 字段在不同接口里可能缺失或为字符串，按可选解析，缺失时排最后。
- 双通道会让"同一首歌出现两次"的风险上升——**去重必须按 `(source, source_id)`**，不能按标题。
- 延迟必须实测；若触发 B 后超过 2s，停下来讨论（可以先砍掉一个 duration 桶）。
