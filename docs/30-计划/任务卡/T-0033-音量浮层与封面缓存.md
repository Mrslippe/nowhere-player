## 1. 背景

真机验收发现两个"每天都会碰到"的小问题。

## 2. 问题一：音量浮层的 `量` 字糊成一团

10px 等宽字体下，中文 `量` 的横画糊成实心块（3× 放大可见），用户看到的是 `音▮ 100%`。

**方案 A（默认）**：文案改成 `VOL 100%` / `VOL 靜音` → `VOL MUTE`。
等宽拉丁在 10px 下极清晰，且更贴合 phosphor 的"设备读数"气质。

**方案 B（备选）**：字号提到 12px，保留中文。代价是浮层变大，会压到副标题。

按 A 做；若产品改主意，改文案与字号即可，不动逻辑。

同时把浮层位置从"进度条上方居中"改为**右上角、时间上方**，避免压在副标题下沿。

## 3. 问题二：重新扫描后封面不刷新

**现象**：扫描 → 某曲目换封面 → 再次扫描 → 播放同一曲目，封面还是旧的。
**根因**：`cover-source.ts` 按 `path → Track` 和 `key → URL` 做了会话内永久缓存，扫描后不清。

**做法**：`library.scan` 完成后（前端收到 done 块）清空两个缓存，并让当前播放曲目重新解析一次。

判据要稳：不要监听块文本，用扫描的**事件**或返回的 `scanId`。若没有现成信号，在 `cmd.exec` 的返回里带一个 `scanEpoch`（递增计数），前端比对变化即清缓存。

## 4. 非目标

- 不做扫描进度 UI。
- 不做封面的多尺寸/预加载。

## 6. 实施要求

1. 音量浮层：文案、位置、字号按方案 A；**保持 1.2s / 180ms 淡出 / 重置计时**的现有行为不变。
2. 缓存失效：清空后必须让**当前播放中**的曲目重新取一次 `coverKey`，否则用户看不到变化。
3. 不要引入 5 秒轮询之类的补丁。

## 7. 验收标准

- [ ] `pnpm -C apps/web test` 全量通过（新增：缓存清空后重新解析、音量文案）
- [ ] `cargo test -p nowhere-desktop` 通过（若加了 scanEpoch）
- [ ] clippy / fmt / typecheck 零问题
- [ ] 真机（主线）：滚轮 → 浮层清晰可读；扫描后播放同一曲目 → 封面更新

## 8. 测试要求

- 缓存失效用假 IPC 计数断言"扫描后重新请求了 track"。
- 音量文案是纯函数（`formatVolume`）测试。

## 9. 文档影响

- 回报中给出：浮层最终文案与位置、缓存失效的触发信号。

## 10. 回报格式

四段式。

## 11. 风险

- **别把缓存清得太狠**：清空 `key → URL` 会导致正在显示的封面闪一下白；只清 `path → Track` 通常就够（因为 coverKey 变了）。
- 若走 `scanEpoch`，注意它必须是**进程内单调递增**，不要用时间戳（时间戳会因时钟调整倒退）。
