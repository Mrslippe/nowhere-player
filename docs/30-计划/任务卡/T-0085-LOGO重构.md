## 1. 真正的根因

art 是**手工逐行敲出来的字符串**，每行内部的字形间距（尤其是补第 7 个 `E` 时追加的空白）**各行不一致**。

具体机制：

```
第 1 行: ███╗   ██╗ ██████╗ …  ███████╗     ← N 与 O 之间 3 空格
第 4 行: ██║╚██╗██║██║   ██║…  ██╔══╝       ← 同样位置 3 空格，但 E 段前多 1 个
```

**行宽补齐只保证"整行等宽"，不保证"同一字母在不同行的列位一致"。**
于是每行的字形整体右移 1–2 列 → 上下半身错位。

**结论：手工字符串无法保证列对齐，必须改成"按字形合成"。**

## 2. 目标：字形表 + 程序合成

### 2.1 数据结构

```rust
/// 每个字形 6 行，行内等宽（构建期断言）。
const GLYPH_N: [&str; 6] = ["███╗   ██╗", "████╗  ██║", ...];
const GLYPH_O: [&str; 6] = [...];
// … O W H E R E
```

### 2.2 合成

```rust
fn compose(letters: &[[&str; 6]; 7]) -> Vec<String> {
    (0..6).map(|row| {
        letters.iter().map(|g| g[row]).collect::<Vec<_>>().join(" ")
    }).collect()
}
```

**对齐由构造保证**：同一行号取每个字形的同一行，列位天然一致。

### 2.3 双重断言（必须都加）

```rust
// 1. 每个字形内部 6 行等宽
for glyph in GLYPHS { assert_eq!(distinct_widths(glyph).len(), 1); }
// 2. 合成后所有行等宽（由 join 保证，仍然断言）
assert_eq!(distinct_widths(&composed).len(), 1);
```

### 2.4 宽度阈值改为运行时计算

```
阈值 = art_width + 边框 2 + 左右留白 2
```

**不再写死 66/68**——写死正是上一轮出问题的原因之一。
