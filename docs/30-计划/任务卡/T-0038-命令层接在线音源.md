| 字段 | 值 |
|---|---|

---

## 1. 背景

音源层能搜能下，但用户在终端里**什么都用不上**：`search` 还是只查本地库，`play` 也不认识在线结果。

这一卡把它接起来，M5 才算闭环。

## 2. 目标

1. `np-sources` 加 `SourceRegistry`：持有多个源，`search_all(query, limit)` 合并结果，单源失败不影响其它。
2. `search` 命令：默认 **本地库 + 在线源**；加 `--local` 只搜本地。结果行首带来源标记。
3. `play <n>` 命中在线结果时：后台线程 resolve → 下载（带进度块）→ `player.play(本地路径)`。
4. 错误文案人话化；过期（403/410）自动重 resolve 一次。
5. 同一曲目并发去重：两个 `play` 打同一首时只下载一次。

## 3. 非目标

- 不做 yt-dlp（T-0037）。
- 不做远程曲目入队（M6——队列元素现在只有路径）。
- 不做封面下载（网易云无 `picUrl`，B 站封面 URL 未接入 UI）。
- 不做设置界面里的源开关。

## 6. 实施要求

### 6.1 `search` 命令语义

| 情形 | 输出 |
|---|---|
| 默认 | 本地在前、在线在后；每行带 `[本地]` / `[B站]` / `[网易云]` |
| `--local` | 只搜本地（行为与现在完全一致） |
| 在线全失败 | 本地结果照常，末尾一条 `hint`：「在线源暂时不可用」 |
| 无任何结果 | 空表 + hint |

序号**统一 1 基、跨源连续**（不是每源从 1 开始）——否则 `play 3` 会有歧义。

### 6.2 `play <n>` 命中在线结果

1. 立即返回 `{ok:true}`，推一个 `running` 块（同 `library scan` 的形态）。
2. 后台线程：resolve → 下载（`progress` 原语，按字节数）→ `player.play(path)`。
3. 完成：该块变 `done`，footer 写「来源：B站 · 已缓存 8.2 MB」。
4. 失败：变 `error`，码与文案按 §6.4。
5. 已缓存：跳过下载，直接播，footer 写「来源：网易云 · 命中缓存」。

### 6.3 并发去重

- 以 `(source, source_id)` 为键，进程内一张 `HashMap<Key, Arc<Mutex<()>>>`；同键串行。
- 两个请求打同一首：第二个等第一个下完，直接命中缓存。

### 6.4 错误与重试

| 情况 | 文案 | 码 |
|---|---|---|
| 版权/会员（`url: null`） | 「该曲目在网易云不可播放（可能版权受限或需要会员）」 | `E_SRC_UNAVAILABLE` |
| resolve 地址过期 | 重 resolve 一次；仍失败 → 「链接已过期，请重新搜索」 | `E_SRC_UNAVAILABLE` |
| 下载中断 | 「下载失败（已清理临时文件）」 | `E_SRC_DOWNLOAD` |
| 网络超时 | 「网络超时，请检查网络或稍后重试」 | `E_NET_TIMEOUT` |
| 源整体不可用 | 该源静默跳过 + hint | — |

### 6.5 进度节流

下载进度按 **时间** 节流（1–2 Hz），复用 T-0023 的 `TimeThrottle` 思路，不要按字节数刷。

## 11. 风险

- **`search` 会变慢**：在线请求 2 个源串行 + 300ms 节流，最坏 1–2 秒才出结果。**先在本地结果后就返回**不可行（表格是一次性渲染的），所以要么接受延迟、要么给"搜索中"的块状态。**选后者**：先推 `running` 块，结果到了再变 `done`。
- **序号跨源连续**这个决定会让「队列序号」和「搜索结果序号」再次并存——`play <n>` 的优先级规则已在 T-0023 定义（队列优先），本卡不改，但**输出里必须写清来源**。
- 下载在后台线程，用户可能在下载中退出应用：要接 `RunEvent::Exit` 取消（复用 T-0023 的 shutdown 路径）。
- 网易云 `expi` 只有 20 分钟，缓存里的文件**不因过期失效**（文件已在本地），只有"重新 resolve 拿新 URL"才受影响。
- 别把 `search` 做成并发请求所有源——并发会触发风控，串行 + 300ms 节流是刻意的。
