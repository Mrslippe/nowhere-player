# 代理角色与交接

> 目的：**不再为每张卡新开代理**。按领域固定几个常驻角色，复用上下文；上下文将满时交接。
> 前提：工具链已固化在 [`scripts/tools/`](../scripts/tools/README.md)，新代理不必重建。

---

## 1. 花名册

| 角色 | 代理 id | 负责范围 | 何时复用 | 何时换新 |
|---|---|---|---|---|
| **UI / 设计** | `76610bdd` | 原型 HTML、CSS、skin、视觉回归 | 同类视觉任务 | 需要"没看过旧方案"的独立评审时 |
| **库 / 扫描** | `6f3a34e6` | `np-library`（SQLite、扫描、封面） | 库域改动 | 换到别的 crate 时 |
| **播放 / 音频** | `cbf6134d` | `np-core` 播放域、`np-audio`、actor | 播放链路 | 涉及 DSP/独占等新领域时 |
| **桌面 / IPC** | `6395e9db` | `src-tauri`、IPC、窗口/托盘 | 壳层改动 | — |
| **验证者** | **每次新开** | 端到端验收 | — | 永远新开 |

**验证者永远新开**是刻意的：它必须没参与实现，否则会顺着实现者的思路找证据，而不是找问题。历史上它三次主动报告"我的脚本错了"，正是因为没有被实现带偏。

## 2. 派发规则

1. **先查花名册**：同类任务用同 id，`send_message` 继续对话即可，不要 `subagent` 新建。
2. **每次派发都重述边界**：常驻代理有旧上下文，可能把上次的临时方案当规范。**契约变了要明说"这条已作废"**。
3. **一角色同时只跑一卡**（串行），不同角色可并行。
4. **范围变化 = 换角色**：`np-core` 的改动交给"播放/音频"，`apps/web` 的交给"UI/设计"，不要跨域。

## 3. 交接（上下文将满时）

角色在自评"上下文用了约 70%"时，写一份状态到 `docs/30-计划/代理状态-<角色>.md`（≤30 行）：

```markdown
## <角色> 状态（<日期>）

- 已完成：<卡号 + 一句话>
- 当前决定：<3–5 条，含"已作废"的旧决定>
- 工具：scripts/tools/*（用法见其 README）
- 踩过的坑：<2–3 条，越具体越好>
- 未决：<交给下一任的事>
```

新代理读这一页 + 当前卡即可接手，成本约 500 token。

> 不要把整段对话摘要塞进交接：**决定和坑比过程重要**。

## 4. 退役

一次性代理（下面这批）**不再恢复**，历史留在会话记录里即可：

T-0001…T-0026 期间的实现者、各轮验证者、设计实验 A/B 组。

判断标准：**它的上下文里没有"下一张卡还需要"的东西**（工具已进仓库，契约已进 docs）。

## 5. 风险

| 风险 | 缓解 |
|---|---|
| 旧假设污染 | 每次派发重述边界；契约变更时点名作废的旧决定 |
| 爆炸半径 | 每卡独立验收 + 视觉回归；验证者独立 |
| 并行度下降 | 常驻代理串行，但不同角色可并行 |
| 交接丢失细节 | 交接只写"决定 + 坑"，不写过程 |
