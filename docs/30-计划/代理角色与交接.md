# 代理角色与交接

> 目的：**不再为每张卡新开代理**。按领域固定几个常驻角色，复用上下文；上下文将满时交接。
> 前提：工具链已固化在 [`scripts/tools/`](../scripts/tools/README.md)，新代理不必重建。

---

## 1. 花名册

> 2026-11-12 重设：项目已转为纯 Rust + Ratatui（ADR-0006），**CSS/Web 与 Tauri 相关角色注销**。

| 角色 | 代理 id | 负责范围 | 何时复用 | 何时换新 |
|---|---|---|---|---|
| **界面层** | `8a1adae1`（暂兼） | `np-tui`：布局、渲染、键位、模式、托盘/热键/启动器 | 同类界面任务 | 需要"没看过旧方案"的独立评审时 |
| **库 / 音源** | `6f3a34e6` | `np-library`、`np-sources`（SQLite、扫描、B站/网易云） | 库域与源域改动 | 换到别的 crate 时 |
| **播放 / 音频** | `cbf6134d` | `np-audio`、`np-core` 播放域、可视化 tap | 播放链路 | 涉及 DSP/独占等新领域时 |
| **验证者** | **每次新开** | 端到端验收 | — | 永远新开 |

**已注销**：

| 角色 | 原因 |
|---|---|
| UI / 设计（`76610bdd`） | CSS/skin/视觉回归随 `apps/web` 一起删除 |
| 桌面 / IPC（`6395e9db`） | `src-tauri` 已删除；托盘/热键/单实例已并入 `np-tui` |

> 现状说明：**大部分卡落在 `np-tui`**，所以界面层暂时由同一个代理串行承担；域级工作可分给库/音源或播放/音频。

**验证者永远新开**是刻意的：它必须没参与实现，否则会顺着实现者的思路找证据，而不是找问题。历史上它三次主动报告"我的脚本错了"，正是因为没有被实现带偏。


## 2. 派发规则

1. **先查花名册**：同类任务用同 id，`send_message` 继续对话即可，不要 `subagent` 新建。
2. **每次派发都重述边界**：常驻代理有旧上下文，可能把上次的临时方案当规范。**契约变了要明说"这条已作废"**。
3. **一角色同时只跑一卡**（串行），不同角色可并行。
4. **范围变化 = 换角色**：`np-tui` 的改动交给「界面层」，`np-library`/`np-sources` 交给「库/音源」，`np-audio`/`np-core` 播放域交给「播放/音频」，不要跨域。
5. **`np-tui` 是单点**：几乎所有界面卡都改它，**同一时间只能跑一张**；要并行，必须一张卡只碰 `np-core`/`np-audio`/`np-library`/`np-sources`。

## 3. 交接（上下文将满时）

角色在自评"上下文用了约 70%"时，写一份状态到 `docs/30-计划/代理状态-<角色>.md`（≤30 行）：

```markdown
## <角色> 状态（<日期>）

- 已完成：<卡号 + 一句话>
- 当前决定：<3–5 条，含"已作废"的旧决定>
- 工具：scripts/tools/*（用法见其 README）
- 踩过的坑：<2–3 条，越具体越好>
- 未决：<交给下一任的事>
```

新代理读这一页 + 当前卡即可接手，成本约 500 token。

> 不要把整段对话摘要塞进交接：**决定和坑比过程重要**。

## 4. 退役

一次性代理（下面这批）**不再恢复**，历史留在会话记录里即可：

T-0001…T-0026 期间的实现者、各轮验证者、设计实验 A/B 组。

判断标准：**它的上下文里没有"下一张卡还需要"的东西**（工具已进仓库，契约已进 docs）。

## 5. 风险

| 风险 | 缓解 |
|---|---|
| 旧假设污染 | 每次派发重述边界；契约变更时点名作废的旧决定 |
| 爆炸半径 | 每卡独立验收 + 视觉回归；验证者独立 |
| 并行度下降 | 常驻代理串行，但不同角色可并行 |
| 交接丢失细节 | 交接只写"决定 + 坑"，不写过程 |

## 6. 上下文连续性与污染

常驻角色省了重建成本，但引入两个风险：**上下文会过期**、**旧决定会复辟**。

### 6.1 三条原则

| 原则 | 做法 |
|---|---|
| **文档是权威，记忆是草稿** | 开工前读 `命令表` / `当前状态` / 设计文档；与记忆冲突时以文档为准 |
| **每张卡声明作废项** | 卡里 §0 明确写「本卡取代哪些旧约定」，代理据此覆盖记忆 |
| **超过两轮交接就轮换** | 同一个角色做过 2 张以上卡后，新卡优先新开代理 + 交接文档 |

### 6.2 什么必须写进交接，什么不能信记忆

| 必须写 | 不能信记忆 |
|---|---|
| 当前生效的参数/形状（数值） | "上次好像是 220ms" |
| 已作废的决定及原因 | "我记得是用 scaleX" |
| 踩过的坑（会复发的） | 文件路径（会变） |
| 未决问题 | 别人的口头承诺 |

### 6.3 主要防线：卡里的「事实基线」

**不靠轮换，靠把事实写进卡。** 每张卡的 §0 列一张表：本卡依赖的、且近期变过的参数/形状/语义。

代理读到冲突时，**以卡为准，覆盖上下文记忆**——不需要换人。

卡里要写的是**会过期的**东西：具体数值、形状、命令语义、字段名。
不需要写：项目结构、构建命令、编码规范（这些稳定，文档里有）。

### 6.4 什么时候才真的轮换

只在**有证据**时轮换，不设硬阈值：

| 证据 | 动作 |
|---|---|
| 某张卡因为"用了旧记忆"导致返工 | 该角色轮换 |
| 同一个决定被该角色改了两次以上 | 轮换（它的记忆里有三个版本） |
| 回报里出现"我记得之前……"且与实际不符 | 轮换 |

**没有证据就不换。** 常驻角色的价值在于连续性，频繁轮换的代价是每次都重建文件知识。
