# 直播画面独立窗口技术方案

> **2026-11-20 实现状态**：T-0105/T-0106 已落地自建 Win32 宿主 + mpv `--wid`；视频模式改为 **mpv 同时输出音视频**，TUI 音频静音保留，见 [ADR-0011](../20-架构/adr/ADR-0011-视频模式mpv音视频主时钟.md)。本文中“np-video 不播放音频 / 以 TUI 音频时钟为主”的早期方案已被取代；以下保留为选型记录。

> 问题：TUI 中继续显示直播画面不现实；若只增加一个“无前端要求”的独立桌面窗口，显示直播画面、支持缩放和 Windows 原生吸附，需要多做多少？

---

## 1. 结论先行

**推荐：独立 `np-video` 子进程 + `eframe/egui` 原生窗口 + FFmpeg 解码。**

- TUI 保留全部控制、音频、弹幕；
- 视频窗口只负责解码和呈现，不做业务 UI；
- 独立进程避免 `winit/eframe` 事件循环与 TUI 主循环互相阻塞；
- 标准 Win32 窗口天然支持拖动、缩放、最大化和 Windows 11 Snap Layouts；
- 不使用 Tauri/WebView2/Electron，避免重新引入 WebView 架构。

**最快验证：先拉起 `mpv` 子进程，1–2 天验证体验；确认值得后再做原生窗口。**

---

## 2. 当前约束

```text
平台：Windows 优先
TUI：Ratatui/crossterm，单二进制
音频：现有 symphonia + cpal 直播链路，900ms 目标缓冲
直播：HTTP-FLV，当前为低延迟只取音频（only_audio=1）
依赖：新增 Rust crate 需明确批准
架构：已移除 Tauri/WebView，不以 WebView 为默认方案
```

---

## 3. 推荐架构

```text
np-tui（终端）
  ├─ 现有音频/弹幕/同接链路
  ├─ 快捷键控制
  └─ 启动/关闭 np-video 子进程
        ├─ 仅视频 URL + 请求头
        ├─ FLV demux + 视频解码
        ├─ 原生窗口 + 纹理呈现
        └─ 窗口关闭/崩溃通知 TUI
```

### 3.1 进程边界

- TUI 不直接创建视频窗口；
- `np-video` 不播放音频，避免与 TUI 音频双声；
- 视频时钟以 TUI 音频时钟为主，帧按 PTS 等待/丢弃；
- 停播、换房、退出时由 TUI 终止旧进程；
- 视频窗口关闭时通过 IPC/退出码通知 TUI。

### 3.2 窗口

使用 `eframe/egui` 或 `winit` 的标准 decorated window：

```text
resizable = true
maximizable = true
decorations = true
```

不实现 borderless/tool window，保留：

- 拖动；
- 边缘缩放；
- 最大化；
- Windows 11 吸附布局；
- 系统 Alt+F4。

## 4. 框架/方案对比

| 方案 | 前端要求 | 缩放/吸附 | 视频能力 | 依赖/成本 | 结论 |
|---|---|---|---|---|---|
| **eframe/egui + FFmpeg** | 无 HTML，纯 Rust UI | 原生窗口，支持 | 纹理呈现，需解码 | FFmpeg 动态库/C 依赖 | **推荐** |
| winit + wgpu + FFmpeg | 最低 | 原生窗口，支持 | 完全自控 | 实现量最大 | 备选 |
| Slint + FFmpeg | 声明式 UI | 原生窗口，支持 | 需自行接 wgpu/纹理 | 生态较小 | 不优先 |
| Tauri/WebView2 + flv.js | HTML/JS | 原生窗口，支持 | HTML5 视频 | 重新引入 WebView | 不推荐 |
| mpv 子进程 | 无 | 原生窗口，基本支持 | 解码最成熟 | 外部 mpv | **MVP 推荐** |
| libmpv 嵌入 | 无 | 取决于宿主窗口 | 解码成熟 | C 库、窗口嵌入复杂 | 备选 |
| Media Foundation | 无 | 原生窗口，支持 | 系统解码，HEVC 受扩展影响 | Windows API 复杂 | 长期备选 |

### 4.1 为什么不用 Tauri/WebView2

- 与“纯 Rust、约 20MB、40ms 启动”的现有目标冲突；
- WebView2 运行时和内存成本高；
- HTML5 直播需要 flv.js/MSE，延迟和音画同步不可控；
- 会把已经删除的 WebView 架构重新引回来。

### 4.2 为什么 mpv 只适合 MVP

- 解码、FLV、硬件加速、窗口一次性解决；
- 但依赖用户安装、无法自定义叠加层、headers/cookie 传递受限；
- 音频必须关闭，仍要处理与 TUI 音频的同步；
- 难以做暂停、换房、窗口状态联动。

## 5. 需要新增的内容

### 5.1 视频源

当前只请求音频：

```text
only_audio=1
```

需要：

```text
only_audio=0
codec=0（H.264，优先兼容）
```

或单独请求一路视频流；音频仍由现有 TUI 链路负责。

### 5.2 FLV demux + 视频解码

- 解析 FLV tag；
- 提取 H.264/HEVC 视频帧；
- 解码为 YUV/RGB；
- 上传 GPU 纹理。

使用 FFmpeg 时约 2–4 天；使用 mpv 时为 0。

### 5.3 音画同步

- 以音频时钟为主；
- 视频帧按 PTS 等待/丢弃；
- 暂停/恢复跟随 TUI；
- 网络抖动时不允许音画分离。

约 1–2 天，是最容易出问题的部分。

### 5.4 窗口生命周期

- 启动/关闭子进程；
- 换房/停播清理；
- 防多开；
- 窗口关闭通知 TUI；
- 视频崩溃不影响音频。

约 0.5–1 天。

### 5.5 原生窗口行为

标准窗口即可获得缩放/吸附；不需要自己实现 Win32 命中测试。约 0.2 天验证。

## 6. 工作量

### 方案 A：mpv 子进程 MVP

```text
窗口进程 + 参数/headers + 生命周期：1 天
缩放/吸附/音画验证：0.5–1 天
合计：1.5–2 天
```

### 方案 B：eframe/egui + FFmpeg

```text
独立进程/IPC：0.5–1 天
视频源 + FLV demux：1–1.5 天
解码 + 纹理：1.5–2.5 天
A/V 同步：1–2 天
生命周期/异常/打包：1 天
合计：5–8 天
```

### 方案 C：Media Foundation

比 FFmpeg 少一个外部动态库，但 Windows API/HEVC 兼容调试更多：

```text
合计：6–10 天
```

## 7. 风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| HEVC 解码兼容 | 黑屏/无声 | 优先 H.264 视频流 |
| 音画漂移 | 体验差 | 以音频时钟为主，按 PTS 校正 |
| FFmpeg 分发 | 安装体积/部署 | 动态库随包或要求系统安装 |
| 双进程生命周期 | 僵尸窗口 | TUI 统一 kill，窗口退出码上报 |
| 窗口焦点/吸附 | 体验问题 | 使用标准 decorated window |
| 资源占用 | 内存上升 | 独立进程可单独监控/退出 |

## 8. 待确认

3. 视频延迟目标：约 1s，还是 2–3s 可接受？
4. 是否需要暂停/恢复、换房、全屏、置顶？
5. 先做 mpv MVP，还是直接 eframe + FFmpeg？

## 9. 建议路线

```text
第一步：mpv 子进程，1–2 天验证窗口/缩放/吸附/音画
第二步：如果值得，再做 eframe + FFmpeg 原生窗口
```

不建议直接上 Tauri/WebView2，也不建议在没有验证的情况下先做完整解码管线。
