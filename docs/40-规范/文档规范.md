# 文档规范

> 目标：让文档**可查、可信、可维护**。文档腐烂比没有文档更糟。
> 2026-11-13 修订：区分“规范类 / 过程类”，补齐自动检查与索引规则。

---

## 1. 四条原则

1. **一篇文档只回答一个问题。** 标题就是那个问题的答案范围。
2. **写给“三个月后的自己”看。** 不写“众所周知”，写清楚为什么。
3. **只写现状与决策，不写愿景。** “以后可能”进 ADR 的备选方案。
4. **能删就删。** 过期文档进 `90-归档/`，不要留在主目录误导人。

---

## 2. 两类文档

| 类型 | 位置 | 例子 | 要求 |
|---|---|---|---|
| **规范类** | `10-设计/`、`20-架构/`、`30-计划/` 的规范页、`40-规范/` | 数据模型、命令表、当前状态、项目结构规范、ADR | front-matter + 进索引 + ≤200 行 + 状态一致 |
| **过程类** | `30-计划/任务卡/`、报告、交接、归档 | T-0086 卡、夜间执行报告、里程碑日志 | 目录入口 + 卡头元信息 + 不再维护时归档 |

**为什么不一刀切**：84 张任务卡如果每张都补 front-matter，成本高于收益；但规范页必须可被脚本检查。
**判断标准**：下一个人会把它当“实现依据”吗？会 → 规范类；只是“当时发生了什么” → 过程类。

---

## 3. Front-matter（规范类必填）

```yaml
---
id: ARCH-003
title: 数据模型
status: active          # draft | active | accepted | deprecated | superseded | archived
owner: 架构师
updated: 2026-11-13     # 任何编辑都要改
verified: 2026-11-13    # 最近一次与代码核对一致
tags: [db, sqlite, contract]
related: [ADR-0007, PLAN-006]
---
```

- **`status`**：`draft` = 评审中，不可作为实现依据；`active` = 可信；`deprecated` = 过期；`superseded` = 被新文档取代；`archived` = 已移入 90。
- **`updated` vs `verified`**：前者是“我改过”，后者是“我对过代码”。超过 60 天未 verified 的 `active` 文档，在索引里标黄并限期复核。
- **`related`**：双向登记；A 引用了 B，B 的 `related` 里也要有 A（至少在一侧有明确链接）。

---

## 4. 单篇结构

1. **一句话结论**（放最前，让人 5 秒判断要不要继续读）
2. **正文**（分节，最多三级标题）
3. **待确认 / 未知**（诚实列出没想清楚的地方）
4. **变更记录**（只记结构性变化，不记错别字）

长度：**≤ 200 行**。超了拆成两篇并在索引里登记；历史长文进 `90-归档/`，不留在主目录。

---

## 5. 写作规则

| 规则 | 说明 |
|---|---|
| 用表格代替长段落 | 尤其是“选项对比”“字段说明”“状态定义” |
| 数字必须带单位与口径 | “内存 160MB”要写清是 RSS 还是工作集、哪个平台 |
| 结论前置 | 先给答案，再给论证 |
| 术语统一 | 以代码与 `np-core` 类型为准；新词先定义再使用 |
| 链接用相对路径 | `../20-架构/数据模型.md`，不要用绝对路径 |
| 图表用 ASCII 或 Mermaid | ASCII 优先（任何环境都能看） |
| 禁止“待补充”超过两周 | 要么写完，要么删掉这一节 |

---

## 6. 生命周期

```
draft ──评审通过──▶ active ──被替代──▶ superseded ──半年后──▶ archived
  │                    │
  └──评审不通过──▶ 删除   └──与代码不符──▶ 立即修正或降级为 draft
```

- **降级触发**：评审者或主线发现文档与代码不一致，当天把 `status` 改回 `draft` 并注明差异。
- **归档**：`deprecated` / `superseded` 满 6 个月且无人引用，移入 `90-归档/`，索引里保留一行“已归档”。
- **ADR 例外**：ADR 不删，只标注 `superseded`；历史决策是资产。

## 7. 同步机制（防腐烂的核心）

| 时机 | 动作 |
|---|---|
| 写代码前 | 先看任务卡的“文档影响”字段 |
| 提 PR / 合并前 | 勾选：□ 行为变更 □ 文档已更新 □ CHANGELOG 已加 |
| 评审时 | 文档守门人核对 G4 门禁（见 SPEC-001 §7） |
| CI | `python scripts/check-docs.py` 检查链接、front-matter、长度、索引 |
| 每月 1 日 | 文档审计：列出所有 `verified` > 60 天的 active 文档，逐篇复核或降级 |
| 里程碑结束 | 更新当前状态，把过期计划文档归档 |

**唯一硬性要求**：改了行为不改文档，PR 不算完成。

---

## 8. 索引与检索

`docs/README.md` 是唯一入口，维护四张表：

1. **规范类文档清单**：ID / 标题 / 状态 / 更新 / 一句话。
2. **过程记录入口**：任务卡目录、报告、归档。
3. **待补清单**：ID / 为什么需要 / 优先级。
4. **路由表**：“我想查 X → 看 Y”，按使用场景而不是按目录组织。

**给智能体用的检索路径**：`AGENTS.md §6 文档路由` → `docs/README.md` → 具体文档。三层之内必须能定位到任何信息。

## 9. ADR（架构决策记录）

位置：`docs/20-架构/adr/ADR-00xx-标题.md`。结构固定四段，**两页以内**：

1. **背景**：什么问题逼着我们做决定
2. **选项**：至少两个，含“什么都不做”
3. **决定**：选了什么，为什么
4. **后果**：接受了什么代价，什么情况下要重新考虑

**什么时候必须写 ADR**：

- 新增/删除 crate 或改变依赖方向；
- 修改已冻结的契约（数据结构、错误码、命令族）；
- 引入新的第三方依赖（尤其是 C 依赖、GPL 许可）；
- 放弃某个已承诺的功能；
- **破坏性数据库迁移**。

ADR 一旦接受就不再修改，只能被新的 ADR 取代（旧 ADR 标 `superseded`）。

---

## 10. 自动检查（check-docs）

`scripts/check-docs.py` 做机械检查，不判断语义：

| 检查 | 规则 |
|---|---|
| 相对链接 | 正文链接目标必须存在；跳过代码块与行内代码 |
| front-matter | 规范类必须含 `id/title/status/updated/verified`，状态在允许集合 |
| 长度 | 规范类 ≤200 行；超长必须在 allowlist 里写明原因 |
| 索引 | 规范类必须在 `docs/README.md` 出现 |
| 已删路径 | `apps/`、`src-tauri`、`pnpm` 等出现时警告；过程文档只汇总，不逐条刷屏 |
| 任务卡 | 必须登记到 `任务卡/README.md`；不强制 front-matter |

**语义是否正确仍然要人抽查**；脚本只能防止结构性腐烂。

---

## 11. 反模式

- ❌ 一篇文档同时讲需求、设计和实现（三层混在一起，改一处要动全篇）
- ❌ 复制粘贴代码到文档里（代码会变，文档不会；贴接口签名可以，贴实现不行）
- ❌ 用“TODO”占位超过两周
- ❌ 索引里登记了但文件不存在 / 文件存在但索引里没有
- ❌ 把决策过程写在聊天里而不落 ADR（三个月后没人记得为什么）
- ❌ 用“文档影响：无”逃避 CHANGELOG
