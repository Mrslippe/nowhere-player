# 文档规范

> ID: SPEC-003 · 状态: 🟢 生效 · 更新: 2026-11-08
> 目标：让文档**可查、可信、可维护**。文档腐烂比没有文档更糟。

---

## 1. 四条原则

1. **一篇文档只回答一个问题。** 标题就是那个问题的答案范围。
2. **写给"三个月后的自己"看。** 不写"众所周知"，写清楚为什么。
3. **只写现状与决策，不写愿景。** 想要"以后可能"的东西，进 ADR 的"备选方案"。
4. **能删就删。** 过期文档进 `90-归档/`，不要留在主目录里误导人。

---

## 2. 分类与编号

| 前缀 | 分类 | 回答的问题 | 变更频率 |
|---|---|---|---|
| `PROD` | 产品 | 做什么、不做什么、给谁做 | 低 |
| `DES` | 设计 | 长什么样、怎么交互、什么状态 | 中 |
| `ARCH` | 架构 | 怎么划分、怎么通信、数据怎么存 | 中 |
| `PLAN` | 计划 | 什么时候做、怎么验收、卡在哪 | 高 |
| `SPEC` | 规范 | 怎么写代码、怎么提交、怎么评审 | 低 |
| `OPS` | 运维 | 怎么构建、怎么发版、怎么排查 | 中 |

编号**永久**：`ARCH-004` 即使改版十次也还是 `ARCH-004`，只升内部版本（v1 → v2），避免链接失效。

目录与编号的对应：

```
docs/00-产品/  → PROD
docs/10-设计/  → DES
docs/20-架构/  → ARCH（含 adr/）
docs/30-计划/  → PLAN
docs/40-规范/  → SPEC
docs/50-运维/  → OPS
docs/90-归档/  → 已废弃，编号保留
```

## 3. Front-matter（每篇必填）

```yaml
---
id: ARCH-004
title: IPC 契约
status: active          # draft | active | deprecated | archived
owner: 架构师
updated: 2026-11-08     # 任何编辑都要改
verified: 2026-11-08    # 最近一次与代码核对一致
tags: [ipc, contract]
related: [ARCH-001, SPEC-001]
---
```

- **`status`**：`draft` = 评审中，不可作为实现依据；`active` = 可信；`deprecated` = 已被替代但保留；`archived` = 移入 90。
- **`updated` vs `verified`**：前者是"我改过"，后者是"我对过代码"。超过 60 天未 verified 的 `active` 文档，在索引里标黄并限期复核。
- **`related`**：双向登记。A 引用了 B，B 的 `related` 里也要有 A。

---

## 4. 单篇结构（默认骨架）

1. **一句话结论**（放最前，让人 5 秒判断要不要继续读）
2. **正文**（分节，最多三级标题）
3. **待确认 / 未知**（诚实列出没想清楚的地方）
4. **变更记录**（只记结构性变化，不记错别字）

长度：**≤ 200 行**。超了拆成两篇并在索引里登记。

---

## 5. 写作规则

| 规则 | 说明 |
|---|---|
| 用表格代替长段落 | 尤其是"选项对比""字段说明""状态定义" |
| 数字必须带单位与口径 | "内存 160MB"要写清是 RSS 还是工作集、哪个平台 |
| 结论前置 | 先给答案，再给论证 |
| 术语统一 | 以 `PROD-002 术语表` 为准（待补）；未定义的新词先加表再使用 |
| 链接用相对路径 | `../20-架构/技术调研-2026-11.md`，不要用绝对路径 |
| 图表用 ASCII 或 Mermaid | ASCII 优先（任何环境都能看） |
| 禁止"待补充"超两周 | 要么写完，要么删掉这一节 |

## 6. 生命周期

```
draft ──评审通过──▶ active ──被替代──▶ deprecated ──半年后──▶ archived
  │                    │
  └──评审不通过──▶ 删除   └──与代码不符──▶ 立即修正或降级为 draft
```

- **降级触发**：评审者或主线发现文档与代码不一致，当天把 `status` 改回 `draft` 并注明差异。
- **归档**：`deprecated` 满 6 个月且无人引用，移入 `90-归档/`，索引里保留一行"已归档"。

## 7. 同步机制（防腐烂的核心）

| 时机 | 动作 |
|---|---|
| 写代码前 | 先看任务卡的"文档影响"字段 |
| 提 PR 时 | PR 模板勾选：□ 行为变更 □ 文档已更新 □ CHANGELOG 已加 |
| 评审时 | 文档守门人核对 G4 门禁（见 SPEC-001 §7） |
| 每月 1 日 | 文档审计：列出所有 `verified` > 60 天的 active 文档，逐篇复核或降级 |
| 里程碑结束 | 更新 PLAN-002，把过期计划文档归档 |

**唯一硬性要求**：改了行为不改文档，PR 不算完成。

## 8. 索引与检索

`docs/README.md` 是唯一入口，维护三张表：

1. **文档清单**：ID / 标题 / 状态 / 更新日期 / 一句话。
2. **待补清单**：ID / 何时必须写完 / 负责阶段。
3. **路由表**："我想查 X → 看 Y"，按使用场景而不是按目录组织。

**给智能体用的检索路径**：`AGENTS.md §6 文档路由` → `docs/README.md` → 具体文档。三层之内必须能定位到任何信息。

未来可加脚本 `scripts/check-docs`：校验 front-matter 完整性、相对链接有效性、`updated` 是否早于文件 mtime。

## 9. ADR（架构决策记录）

位置：`docs/20-架构/adr/ADR-0001-标题.md`

结构固定四段，**两页以内**：

1. **背景**：什么问题逼着我们做决定
2. **选项**：至少两个，含"什么都不做"
3. **决定**：选了什么，为什么
4. **后果**：接受了什么代价，什么情况下要重新考虑

**什么时候必须写 ADR**：

- 新增/删除 crate 或改变依赖方向
- 修改已冻结的契约（IPC、数据结构、错误码）
- 引入新的第三方依赖（尤其是 C 依赖、GPL 许可）
- 放弃某个已承诺的功能

ADR 一旦接受就不再修改，只能被新的 ADR 取代（旧 ADR 标 `superseded by ADR-00xx`）。

## 10. 反模式

- ❌ 一篇文档同时讲需求、设计和实现（三层混在一起，改一处要动全篇）
- ❌ 复制粘贴代码到文档里（代码会变，文档不会；贴接口签名可以，贴实现不行）
- ❌ 用"TODO"占位超过两周
- ❌ 索引里登记了但文件不存在 / 文件存在但索引里没有
- ❌ 把决策过程写在聊天里而不落 ADR（三个月后没人记得为什么）
