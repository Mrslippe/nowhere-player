# 智能体工作管线

> ID: SPEC-001 · 状态: 🟢 生效 · 更新: 2026-11-08
> 适用范围：本项目的全部代码实现工作。主线对话不写业务代码，只做架构、出卡、评审与集成。

---

## 1. 四条基本原则

1. **契约先行**：任何跨模块的接口、数据结构、错误码，先写进文档并冻结，再允许并行施工。没有契约的并行等于制造冲突。
2. **可验证即完成**：任务卡上的每条验收标准都必须能被一条命令或一次观察证明。"看起来没问题"不算完成。
3. **单一所有权**：同一时刻，一个文件只能有一个智能体在改。冲突靠排期避免，不靠合并解决。
4. **主线兜底**：流程是为了提速，不是为了表演。任何环节卡住超过 2 轮，立刻收回主线处理。

---

## 2. 角色

| 角色 | 谁 | 职责 | 绝对不做 |
|---|---|---|---|
| **架构师** | 主线对话 | 需求澄清、第一轮方案、任务卡、契约、评审裁决、集成、验收 | 不写业务代码 |
| **实现者** | 子智能体（每卡一个） | 按卡施工、自检、按格式回报 | 不改契约、不加依赖、不越界 |
| **评审者** | 另一个子智能体 | 对抗式审查：找 bug、越界、缺测试、与规范不符 | 不参与实现，不改代码 |
| **验证者** | 可与评审者合并 | 跑门禁命令，产出结果表 | 不判断设计好坏 |
| **文档守门人** | 架构师 / 评审者兼任 | 检查"行为变了，文档是否跟着变" | — |

**为什么主线不写业务代码**：保证架构视角不被实现细节绑架。但主线保留三项权力——**写任务卡、改胶水（≤30 行的接线/配置）、修阻塞性 bug**。没有这三项，一个三行编译错误也要开一次子智能体，流程会先压垮项目。

## 3. 工作流

```
P0 方案/确认 ──▶ S0 立项 ──▶ S1 契约 ──▶ S2 实现 ──▶ S3 门禁 ──▶ S4 评审 ──▶ S5 修复 ──▶ S6 集成 ──▶ S7 验收
  主线+用户       主线      主线+评审    实现者       自动       评审者      实现者       主线      主线+用户
```

| 阶段 | 产出 | 通过条件 |
|---|---|---|
| **P0 方案** | 只读分析 + 方案（范围/分级/授权/分配/验证） | 用户明确确认 |
| **S0 立项** | 任务卡（模板见 PLAN-003） | 验收标准可执行、授权路径明确、依赖已合并 |
| **S1 契约** | 契约文档更新（ARCH-00x） | 评审者确认"照此实现不会产生歧义" |
| **S2 实现** | 代码 + 自检报告 | 实现者自报"门禁全绿" |
| **S3 门禁** | 命令输出 | fmt / clippy / test / docs 全过 |
| **S4 评审** | 评审报告（PASS / PASS-WITH-NITS / BLOCK） | 无 BLOCK 项；NITS 可延后 |
| **S5 修复** | 新提交 | 最多 2 轮；超轮次回主线 |
| **S6 集成** | 合并 + CHANGELOG + 文档同步 | G4（文档门禁）通过 |
| **S7 验收** | 验收记录（写回任务卡） | 验收清单逐条勾选 |

> **S1 可跳过**：纯 UI 样式、纯文档、单文件内部重构这类不产生跨模块契约的任务，直接 S0→S2。

### 3.1 方案门（P0，2026-11-17）

任何改动请求（代码/文档/配置/流程），第一轮只做只读分析并给出执行方案，不改文件、不提交、不构建、不重启。

方案必须包含：

1. 现状/根因
2. 目标与验收标准
3. 范围/非目标
4. C0-C4 级别 + T0-T3 验证级别
5. 授权路径（文件白名单）
6. 工作拆分与子智能体分配
7. 风险/待决策

确认语义：

- “确认 / 开始 / 按这个做 / 执行” → 下一轮施工。
- 只提问、改方案、补充信息 → 继续出方案，仍不动手。
- 信息不足 → 可只问澄清问题；澄清后仍先出方案。

例外：

- 纯提问、状态查询、只读诊断可直接回答；一旦需要改动，先停下出方案。
- 用户明确说“跳过方案，直接改” → 可执行，但回复首行标注“已跳过方案门”，并在任务卡记录。

## 4. 任务卡：唯一的接口

任务卡是主线与实现者之间**唯一**的信息载体。子智能体拿不到本对话的上下文，所以卡片必须自包含。

必填字段（完整模板见 PLAN-003）：

| 字段 | 要求 |
|---|---|
| ID / 标题 | `T-0007 播放器小窗静态原型` |
| 背景 | 最多 3 句，讲清楚"为什么现在做这个" |
| 目标 | 可验证的结果，不写实现方式 |
| 非目标 | 明确排除，防止范围蔓延 |
| 输入 | 必读文档路径（≤5 个）+ 已冻结的契约 |
| 授权路径 | 可写文件/目录清单（白名单） |
| 禁止改动 | 常见越界点（如 `Cargo.toml`、`docs/20-架构/`） |
| 验收标准 | 逐条可执行，例如"窗口打开耗时 < 300ms" |
| 测试要求 | 必须新增哪些测试，或写明豁免理由 |
| 文档影响 | 需要同步更新哪篇文档 |
| 回报格式 | 固定四段（摘要/验证/未决/文档） |

**卡片规模上限**：单人 1–2 天可完成；改动 ≤ 400 行；涉及文件 ≤ 12 个。超了就拆卡。

## 5. 并行规则

只有在**契约已冻结**的前提下才允许并行。

| 规则 | 说明 |
|---|---|
| **文件所有权** | 并行任务的 `授权路径` 不得重叠；共享文件（如 `lib.rs` 的模块声明）由主线统一改 |
| **合并顺序** | 契约提供方先合，消费方后合；数据层先合，UI 后合 |
| **并行度 ≤ 3** | 超过 3 个并行任务，评审质量会明显下降 |
| **每日一同步** | 并行的分支每天至少向主线 rebase 一次，避免大冲突 |
| **契约变更即冻结** | 任何一方发现契约不够用，立即停手提 ADR，不许"先改了再说" |

**适合并行**：三个音源适配器、多个 UI 组件、三平台打包脚本。
**不适合并行**：同一模块的重构、有强顺序依赖的迁移、调试类问题。

### 5.1 纯 Rust 时代的新约束（2026-11-12）

迁移后**并行度显著下降**：以前 `crates/**` 与 `apps/web/**` 天然可分，现在**几乎所有界面卡都改 `np-tui`**。

| 规则 | 说明 |
|---|---|
| **`np-tui` 单点串行** | 同一时间只能有一张卡改 `np-tui`，否则必撞 |
| **按 crate 分域并行** | `np-library` / `np-sources` / `np-audio` / `np-core` 之间可并行 |
| **跨域卡先拆** | 一张卡同时要改 `np-tui` 和 `np-app` → 拆成两张，先合被依赖方 |
| **主线做胶水** | 跨 crate 的接线（如 `ThemeApplyReply` 加字段）由主线直接改，不派发 |

## 6. 上下文投喂

| 内容 | 给不给 |
|---|---|
| 任务卡全文 | ✅ 必给 |
| 相关文档（3–5 篇，给路径与要点摘要） | ✅ |
| 已冻结的契约 | ✅ 全文 |
| 最近的目录树 | ✅ |
| 完整对话历史 | ❌ 不给（噪声大、成本高） |
| 其他任务的实现细节 | ❌ 不给（避免模仿错误） |

**例外**：评审任务可以用"继承对话"的方式启动，因为它需要判断"这次改动是否符合当初的意图"。

**给路径，不给内容**：让智能体自己读文件，比在提示词里粘贴大段代码更可靠，也更省 token。

## 7. 质量门禁

| 门禁 | 检查项 | 谁来查 | 不通过的处理 |
|---|---|---|---|
| **G1 可构建** | fmt、clippy `-D warnings`、test 编译 | 自动 | 实现者自行修 |
| **G2 可验证** | 单测通过；新增逻辑有测试或书面豁免 | 自动 | 补测试 |
| **G3 不越界** | 改动文件 ⊆ 授权路径；无新依赖；无契约变更 | 评审者 | 直接 BLOCK，重发卡 |
| **G4 文档同步** | 行为变更 → 对应文档已更新；CHANGELOG 有条目 | 文档守门人 | 补文档后重审 |
| **G5 验收达成** | 任务卡验收标准逐条勾选 | 主线 | 返工或拆卡 |

**G3 是最高频的失败点**，评审者必须逐文件核对 diff，不能只看摘要。

### 7.1 收口门禁（G6，2026-11-13 新增）

功能/测试通过不等于卡完成。合并前还要满足：

| 检查 | 证据 |
|---|---|
| 文档同步 | 任务卡“文档影响”逐条勾选；`check-docs` 绿 |
| ADR | schema / 错误码 / 命令族 / 依赖变化有对应 ADR |
| 死代码 | 删除/重构卡无新增 `allow(dead_code)`；残留词扫描为零 |
| 发布 | `CHANGELOG` 有行；版本/tag 规则满足 |
| 工作区 | `git status` 干净，无临时文件/截图 |
| 评审 | 卡尾有 review verdict 与验收人 |

**没有 G6 的卡，不允许打 base tag。** 这条是 T-0079 只删一半、文档留债的直接修复。

### 7.2 验证分级（2026-11-17）

G1～G6 的完整执行按 [`SPEC-007`](子智能体协作架构.md) 分级：

```text
C0 微改 → T0：cargo check + 定向测试
C1 小改 → T1：crate tests + clippy
C2 功能 → T2：workspace tests + fmt + clippy + docs/contracts
C3 架构 → T3：check.ps1 + release/PTY
```

C0/C1 可裁剪门禁；C2/C3 必须完整执行。红线（契约、依赖、越界、敏感数据）不随级别裁剪。

### 7.3 可见性证据（G5 的硬性要求）

**凡是"选中 / 激活 / 当前 / 高亮"这类状态，验收必须带可见性证据，不能只断言 class 或属性。**

| 要证明的 | 不够 | 必须 |
|---|---|---|
| 某一行被选中 | `aria-selected === "true"` | 选中第 1 项与第 2 项时，**同一坐标的像素值不同**；或 3× 放大图能肉眼分辨 |
| 弹层内容已更新 | 输入框 `value` 变了 | 弹层内文本/条数已变 |
| 边框存在 | `box-shadow` 计算值正确 | 截图上能看见，且浅色背景也可见 |
| 动效在动 | CSS 里写了 transition | 中间帧截图（首尾两帧不算） |

**为什么**：状态"存在"与状态"可见"是两件事。开发时自己试往往觉得能用——因为刚敲了键，心里知道它应该在哪。
**中间帧证据的正确写法**：声明「在 `0 < t < duration` 的某个时刻采样，记录实际值」，**不规定具体数值**。

> 反例（真实踩过，2026-11-11）：验收写「50% 时刻 opacity ≈ 0.5」，实现者为达标加了一个 `50% { opacity: .5 }` 关键帧，
> 把 `cubic-bezier(.3,0,.8,.15)` 的正常形态（约 0.8）压成了 0.5——**动画被改坏，测试变绿**。
>
> **数值出现在验收标准里时，先问：这是目标，还是采样点？**


**真实失败案例（2026-11-11）**：

| 卡 | 断言 | 实际 |
|---|---|---|
| 候选上下选择 | `aria-selected` 从 false 变 true | 选中背景与弹层底色只差 6 个 RGB 级差，**肉眼看不见**，用户报"功能没有" |
| Tab 采纳 | 输入框 value 变成 `play ` | 弹层仍显示旧候选 |

两例都"逻辑正确、用户无感"。

## 8. 例外与升级

| 情况 | 处理 |
|---|---|
| 编译不过，2 轮内没解决 | 回主线，由主线直接修（行使"修阻塞 bug"权） |
| 实现者认为任务卡有歧义 | **停手**，在回报里写"需澄清：X"，不要猜 |
| 发现必须改授权路径外的文件 | 停手报告，由主线改卡或改契约 |
| 评审与实现僵持 | 主线裁决，结论写进 ADR，避免下次再吵 |
| 任务反复做不对（≥2 次） | 拆成更小的卡；或主线先写 20 行骨架（stub），实现者只填实现 |
| 需要新依赖 | 提交"依赖申请"：用途、体积、许可、替代方案，主线批准后写进卡 |

**ADR（架构决策记录）**：任何"会改变结构/契约/依赖"的决定，都要在 `docs/20-架构/adr/` 留一篇两页以内的记录——背景、选项、决定、后果。这是唯一允许"写下来就不用再解释"的地方。

## 9. 什么时候用"多智能体编排"

| 场景 | 方式 |
|---|---|
| 1 个任务，顺序明确 | 单个子智能体 |
| 2–3 个互不依赖的任务 | 并行发 2–3 个子智能体 |
| ≥4 个同构任务（如 3 个音源 + 各自测试） | 用 workflow 脚本 fan-out，带阶段与结构化结果 |
| 需要"实现 + 独立评审"成对出现 | 两个子智能体，评审者拿不到实现者的推理过程 |

**反模式**：为了让流程"看起来专业"而把一个 30 行的改动拆成 3 个智能体。流程开销必须小于收益。

## 10. 轻量化：前两个里程碑用简化模式

完整双评审的成本不低。建议：

| 阶段 | 模式 |
|---|---|
| **M0–M1** | 简化：任务卡 → 实现 → 自检 → **主线评审**（不设独立评审者） |
| **M2 起** | 完整：增加独立评审者 + 文档守门人 |
| **M4 起（音源）** | 加严：涉及加密/网络的任务必须有夹具测试 + 二次评审 |

理由：早期改动集中在骨架和视觉，主线看得过来；等模块多起来、并发高起来，再上双评审。

## 12. 管线自身的迭代

这套流程不是一次定死的。每个里程碑结束时回答三个问题，写进 [`当前状态`](../30-计划/当前状态.md) 的“欠账/下一步”，或单独开一张流程改进卡：

1. 哪类任务返工最多？→ 补对应的规范或模板字段。
2. 哪个门禁从没拦住过问题？→ 删掉，别养仪式。
3. 主线花在协调上的时间占比多少？> 30% 说明卡片粒度不对。

## 13. 失败与恢复

### 13.1 四类失败

| 类别 | 典型现象 | 责任方 | 处理 |
|---|---|---|---|
| **A 环境** | 依赖拉不下来、权限拒绝、磁盘满、工具缺失、代理不通 | 无（环境问题） | 重试 1 次；仍失败 → **停手报告**，由人决定换网络/装工具。禁止绕过（换镜像源、改权限、关校验） |
| **B 任务** | 卡片有歧义、验收标准不可达、依赖未合、范围超载 | 主线 | 改卡重发；不追究实现者，这是卡的问题 |
| **C 执行** | 越界改文件、私自加依赖、伪造验证结果、死循环重试 | 实现者 | 判定 BLOCK → 回滚到基线 → 拆小卡，或主线先写骨架 |
| **D 运行时** | 超时无返回、进程挂死、上下文耗尽、崩溃 | 平台 | 检查工作区 → 判定产物状态 → 接管或重发 |

### 13.2 派发前必做（三条）

1. 工作区干净（`git status --short` 为空），并打基线标签 `base/T-XXXX`。
2. 依赖已合并且门禁为绿。
3. 卡片已填"时间预算"。

### 13.3 实现者的增量提交义务

每完成一个**可验证的小步**就提交一次（`wip(T-XXXX): ...` 允许）。
理由：挂起时产物可评审、可续做；避免"跑了 20 分钟什么都没留下"。
一次大提交 = 失败时全部作废。

### 13.4 超时判定

- **到库存预算 80%**：主线主动检查工作区——有没有新文件、有没有进程在跑、有没有 commit。
- **到 100%**：**强制作出判定**，不等自动返回：
  - 产物可验证且门禁绿 → 主线接管提交，记为"完成但未回报"。
  - 产物不完整 → interrupt → 回滚到基线 → 重发（附断点说明）。
  - 同一张卡连续两次失败 → 拆卡，或主线直接实现。

### 13.5 重发规则

重发必须附：**上次做到哪、已存在哪些文件、从哪继续、禁止覆盖什么**。
不允许"原样再发一次"——那是赌博，不是重试。

### 13.6 记录

每次失败在 [`当前状态`](../30-计划/当前状态.md) 的欠账表或 `docs/90-归档/` 的复盘记录里记一行：卡号、类别、现象、处置、耗时损失。
同类失败连续出现两次 → 改流程或改模板，而不是催执行者。

### 13.7 为什么这套能兜住

任务卡负责**范围**，git 负责**状态**，门禁负责**真伪**。
三者独立：智能体挂了，卡片还在；进度丢了，基线还在；报告不可信，命令输出还是可信的。

## 14. TUI 卡的收敛规则（2026-11-12 修订）

> 原为「前端卡的收敛规则」（2026-11-11），针对 Web 前端"验证必须看图"而写。
> 迁到 Ratatui 后**前端不存在了**，但"证据要便宜且可靠"这条原则反而更强。
> 本章按纯 Rust + TUI 重写。

### 14.1 三档证据，先便宜后贵

| 档 | 手段 | 成本 | 适用 |
|---|---|---|---|
| **1. 文本** | `cargo test` 断言 / `NP_TUI_SELFTEST="…"` 输出 | **极低** | 命令结果、播放状态、搜索、主题、错误路径 |
| **2. 像素** | 截图采样 / 尺寸与坐标测量 | 中 | 布局、对齐、配色、字符画 |
| **3. 人眼** | 人看 / 人听 | 高（要等人） | 手感、观感、**声音**、托盘点击、媒体键 |

**规则：能用第 1 档就不用第 2 档，能用第 2 档就不用第 3 档。**

#### 首选：无头自检

```bash
NP_TUI_SELFTEST="search 晴天;play 2" target/release/np-tui.exe
```

输出是**可 diff 的文本**，比截图便宜一到两个数量级，且不受窗口焦点影响（曾因抢焦点卡住三个验收）。

#### 其次：像素断言

「看得见的错，不一定是错；量出来的才算。」
2026-11-11 我在 1× 截图上"看"出表头错位，实测差值 **0**。

#### 最后：人眼

只用于**无法量化**的项：声音是否可闻、媒体键是否响应、观感是否舒服。

### 14.2 四条硬规则

#### ① 把"看"换成"量"

验收标准必须写成**可测量的断言**，代理报**数字**而不是截图。

| 不行 | 可以 |
|---|---|
| 「高亮在第二项」 | 「`activeIndex=1` 时 item2 左缘像素 `(255,180,84)`，item1 为 `(26,30,36)`」 |
| 「表头与数值对齐」 | 「表头右边缘 728，数值右边缘 728，差值 0」 |
| 「阴影没有被裁切」 | 「卡片外 10px 处像素 `(x,y,z)` 与壁纸底色不同」 |
| 「边框可见」 | 「浅色壁纸下边框与卡底 RGB 差 ≥ 9」 |

**真实教训**：2026-11-11 体检时，我在 1× 截图上"看"出表头错位，一量差值是 **0**——**看得见的错，不一定是错；量出来的才算。**

#### ② 视觉回归脚本化

用 [`scripts/tools/png-hash.mjs`](../../scripts/tools/png-hash.mjs) 对比基线：

```bash
node scripts/tools/png-hash.mjs --dir tmp/before --dir tmp/after
```

代理**只报结论**：`9/9 相同` 或 `3 张不同（列出文件名）`。**不把图贴进报告。**

只有"必须人眼判断"的情形才允许附图，且**最多 1 张**。

#### ③ 单卡条目上限 3

一张前端卡最多 3 个条目。超出就拆卡。

理由：条目数 ≈ 报告长度 ≈ 返工面积。8 条、9 条的卡，报告都写成了长文，其中一半是复述需求。

#### ④ 前端报告格式收紧

```markdown
## 变更摘要      ≤ 10 行，只写"改了什么、为什么"
## 验证         只报数字：尺寸 / 差值 / 像素 / 耗时 / 测试数
## 未决 / 风险   ≤ 5 条
## 文档影响      ≤ 3 条
```

- **禁止**贴多张对比图（回归用脚本，结论用数字）。
- **禁止**复述卡里的需求原文。
- 附图需说明"为什么这张图不能被数字代替"。

### 14.3 什么时候必须真的看

| 情形 | 必须人眼 |
|---|---|
| 声音是否真的出来 | **是**（唯一无法自动化的核心功能） |
| 媒体键 / 托盘点击 / 开机自启 | 是（需要人按键重启） |
| 排版观感（留白、密度、配色和谐） | 是 |
| 位置/尺寸/对齐/边框存在性 | **否，必须测量** |
| 状态是否变化（选中、激活） | **否，必须像素或采样** |
| 命令结果、播放状态、错误文案 | **否，必须文本断言** |

### 14.4 生效方式

- 写卡时，**每条验收标准后面标注证据类型**：`[数字]` / `[图]` / `[人工]`。
- 标 `[图]` 的条目，卡里要说明为什么不能量化。
- 评审时，`[数字]` 条目用图交差视为**未完成**。
- 标 `[人工]` 的条目必须写清"谁来验、怎么验"，并**排进醒来后的清单，不要阻塞其它工作**。
- **每张卡至少给一条可复现命令**（`cargo test …` 或 `NP_TUI_SELFTEST="…"`），否则验收只能靠口述。

## 15. 疑难杂症：先查社区，再动手

> **教训（2026-11-12）**：终端光标闪烁，我先给了「稳态光标 / 降帧 / 条件跳过」三个补丁，
> 产品问"别的项目怎么处理"，才查到 **DECSET 2026 同步更新**——一个序列解决全部问题。
>
> **补丁是自己想的，标准解在社区里。**

### 15.1 判定：什么算"疑难杂症"

出现下列任一信号，**停止自行设计，先去查**：

| 信号 | 例子 |
|---|---|
| 现象是"视觉的、偶发的" | 闪烁、撕裂、错位 |
| 已有一个补丁但治标不治本 | 降帧能缓解但没根除 |
| 涉及平台差异 | 只在 Windows / 只在 ConPTY 出现 |
| 你在"试参数" | 20fps→12fps、加 1px 偏移 |
| 协议/序列级问题 | 光标、颜色、宽字符 |

### 15.2 查哪里（按顺序）

1. **终端控制序列标准**：先查有没有对应的 CSI 序列（同步更新、DECCKM、bracketed paste…）
2. **上游仓库的 issue / discussions**：`ratatui`、`crossterm`、`Windows Terminal` 的 issue 搜索
3. **同类开源项目的 commit 信息**：它们踩过，提交信息里通常直接写原因
   - 例：`fix(renga): apply frame-end caret as MoveTo->Show to stop conpty flicker`
   - 例：`fix(tui): enhance flicker prevention for Windows terminals with DECSET 2026`
4. **规范/约定**：`no-color.org`、`specs` 类站点

### 15.3 关键词模板

```
<现象> <库名> site:github.com
<现象> <平台> fix
"<现象>" commit
```

例：`cursor flicker conpty fix` 直接命中 renga 与 CodeWhale 的提交。

### 15.4 查到之后的动作

- 社区有标准解 → **用标准的**，并在卡里写明来源与链接；
- 社区只有零散补丁 → 选"最接近根因"的那个，并记为技术债；
- 确实没有 → 自己造，但**在卡里写明"已检索，无现成方案"**（避免下一个人重复查）。

### 15.5 反面教材（本次）

| 我给的 | 性质 |
|---|---|
| 稳态方块光标 | 减弱现象 |
| 20fps → 12fps | 减弱现象（附带省 CPU，保留） |
| 位置不变跳过移动 | 缩小窗口，还引入 IME 风险 |
| **DECSET 2026** | **根因解**（终端原子呈现整帧） |

## 16. TUI 布局问题：先 dump 字符网格，再考虑截图（2026-11-12）

> 教训：启动页 logo 被判定"上下错位"，用截图反复排查三轮，
> 实际字符网格一直是对的——**错位来自字体（Sarasa Mono CL Bold 的制表符不接缝）**。

### 16.1 顺序

| 步骤 | 证据 | 能回答什么 |
|---|---|---|
| 1 | **金标文件 / `TestBackend` dump** | 列对不对、宽度多少、有没有溢出 |
| 2 | 文字测量（起始列、行宽、字符数） | 对齐、间距、截断 |
| 3 | 截图 | **只有**字体渲染、颜色、字重、抗锯齿 |

**布局问题用截图，等于把字体变量混进排版结论。**

### 16.2 两条硬规则

1. 任何"错位/对不齐"的报障，**先打印字符网格并量列号**；
2. 截图的结论必须写明它是"字体渲染"还是"网格内容"——**两者不能混说**。

### 16.3 本次实例给出的判据

网格正确（6 行全部 67 列、起始列一致）而截图显示断裂
→ **只能是字体渲染**，换 Cascadia Mono 后立即正常，验证成立。
