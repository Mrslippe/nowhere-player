# 项目结构规范

> ID: SPEC-002 · 状态: 🟢 生效 · 更新: 2026-11-08
> 目标：让"加一个功能"永远只动应该动的地方；让新人（或新智能体）十分钟内知道该去哪。

---

## 1. 三条总则

1. **单一职责**：一个 crate / 一个目录，只回答一个问题。
2. **单向依赖**：依赖只能从上往下流，禁止环、禁止反向。
3. **随时可运行**：主干任何时刻都能 `cargo build` + `pnpm dev` 通过。半成品用 feature flag 挡住，不用注释挡住。

---

## 2. 目录结构

```
nowhereplayer/
├─ AGENTS.md                  # 智能体入口（必读）
├─ README.md                  # 人类入口（截图、安装、一句话）
├─ CHANGELOG.md               # 版本变更
├─ Cargo.toml                 # Rust workspace
├─ rust-toolchain.toml        # 工具链锁定
├─ .editorconfig
├─ .gitattributes             # 行尾统一 LF
├─ .gitignore
│
├─ docs/                      # 全部文档，见 docs/README.md
│
├─ crates/                    # 纯 Rust，无 UI 依赖
│  ├─ np-core/                # 领域模型、Command、事件、错误码、配置结构
│  ├─ np-audio/               # 解码、重采样、混音、输出、播放状态机
│  ├─ np-library/             # 扫描、标签、封面缓存、SQLite、检索
│  ├─ np-sources/             # MusicSource trait + local/netease/bilibili/ytdlp
│  └─ np-system/              # 托盘、媒体键、单实例、自启、窗口控制
│
├─ apps/
│  ├─ desktop/                # Tauri 壳
│  │  ├─ package.json         # @tauri-apps/cli 脚本
│  │  └─ src-tauri/           # 独立 crate，同时是 workspace 成员
│  │     ├─ Cargo.toml
│  │     ├─ build.rs
│  │     ├─ tauri.conf.json
│  │     ├─ capabilities/     # 权限声明
│  │     ├─ icons/
│  │     └─ src/              # 窗口装配、命令注册、IPC 适配
│  └─ web/                    # React 前端
│     ├─ src/
│     │  ├─ app/              # 入口、路由、窗口初始化
│     │  ├─ design/           # token、全局样式、基础组件
│     │  ├─ features/         # player/ terminal/ library/ settings/
│     │  └─ shared/           # ipc、hooks、utils、类型
│     ├─ index.html
│     └─ vite.config.ts
│
├─ assets/                    # 图标源文件、字体、截图（构建产物不放这里）
├─ scripts/                   # check / build / release / 文档校验
└─ .github/workflows/         # CI
```

**为什么不放 `src-tauri/` 到根**：`apps/desktop` 与 `apps/web` 是并列的两个应用单元，Tauri 只是其中一个的壳；扁平化能避免"根目录即 Tauri 项目"的误解。

## 3. 依赖方向

```
        apps/desktop ──▶ apps/web（仅静态资源）
             │
             ▼
        crates/np-system
             │
             ▼
   ┌──── np-library ──── np-sources ────┐
   │            │            │          │
   └────────────┴──▶ np-core ◀──────────┘
                       ▲
                       │
                  crates/np-audio
```

| 规则 | 违反示例 |
|---|---|
| `np-core` 不依赖任何 `np-*` | core 里 `use np_audio::Player` ❌ |
| `np-*` 不依赖 `apps/*` | 库里 `use tauri::AppHandle` ❌ |
| `np-*` 之间不互相依赖（除 core） | `np-library` 依赖 `np-sources` ❌ |
| `apps/web` 不直接读数据库/文件 | 前端自己 `sqlite` 查询 ❌ |
| 禁止 `np-audio` ↔ `np-library` 双向 | 需要交互时通过 core 定义的事件 |

**跨模块通信只走两种方式**：`np-core` 里定义的类型/事件，或 `np-core` 里定义的 trait。

---

## 4. crate 职责边界

| crate | 负责 | 明确不负责 |
|---|---|---|
| `np-core` | `Track`/`Queue`/`PlaybackState` 模型；`Command` 与 `Spec`；错误码；配置结构；事件定义 | 任何 IO、任何第三方重依赖 |
| `np-audio` | 解码、重采样、混音、cpal 输出、播放状态机、位置上报 | 网络、数据库、UI |
| `np-library` | 文件遍历、标签解析、封面缓存、SQLite、查询 | 播放、网络音源 |
| `np-sources` | 音源协议实现、URL 解析、可播性判定 | 播放、入库（入库由 library 负责） |
| `np-system` | 托盘、媒体键、单实例、自启、窗口显示/隐藏 | 业务状态 |

**判据**：如果一个功能同时需要"网络 + 解码 + 入库"，那它不是某一个 crate 的事，而是 `apps/desktop` 里的编排逻辑（薄），或 core 里定义的事件流。

---

## 5. 前端目录边界

| 目录 | 允许 | 禁止 |
|---|---|---|
| `app/` | 路由、窗口初始化、全局 Provider | 业务逻辑 |
| `design/` | token、reset、基础组件（Button/Icon/Progress） | 依赖 `features/` |
| `features/player/` | 播放器窗口的全部 UI 与本地状态 | import `features/terminal/` |
| `features/terminal/` | 终端窗口的全部 UI 与本地状态 | import `features/player/` |
| `shared/` | IPC 封装、hooks、工具函数、共享类型 | 依赖任何 `features/` |

**`features/` 之间零 import**。要共享，往上提到 `shared/` 或 `design/`。

## 6. 命名

| 对象 | 规则 | 示例 |
|---|---|---|
| Rust crate | `np-` 前缀 + kebab | `np-audio` |
| Rust 模块 | snake_case | `playback_state.rs` |
| Rust 类型 | PascalCase，语义完整 | `PlaybackState`、`SourceId` |
| TS 组件 | PascalCase 文件 | `PlayerCard.tsx` |
| TS 工具/钩子 | kebab + 后缀 | `use-player-state.ts` |
| CSS 变量 | `--区域-属性` | `--player-accent`、`--term-bg` |
| 文档 | `NN-分类/中文标题.md` | `10-设计/播放器小窗.md` |
| 任务卡 | `T-0007-短横线标题.md` | `T-0007-player-window-prototype.md` |
| 分支 | `t/0007-player-window` | 与卡号绑定 |
| 提交 | Conventional Commits | `feat(player): 增加悬停控制条` |

## 7. 迭代规则

| 规则 | 说明 |
|---|---|
| **主干开发** | trunk-based；分支生命周期 ≤ 3 天；不允许长期 `develop` |
| **小步提交** | 单 PR ≤ 400 行；超过就拆 |
| **每次提交可构建** | 不允许"下次再修"的中间态进主干 |
| **行为变更必带文档** | 同 PR 更新对应文档与 CHANGELOG |
| **数据库变更必带迁移** | 迁移只增不改；每次升级前自动备份 |
| **未完成功能用 feature flag** | 默认关闭，不删代码、不注释 |
| **破坏性变更靠版本号** | `0.x` 阶段允许破坏，但必须在 CHANGELOG 写清楚 |

## 8. 什么时候才允许"加一层"

过早抽象是本项目最大的结构性风险。判据：

| 动作 | 允许的前提 |
|---|---|
| 新增 crate | 现有 crate 的职责已经说不清，且有 ≥ 2 个明确的使用方 |
| 抽 trait | **已知**有 ≥ 2 个实现（`MusicSource` 属于此类，一开始就有 4 个） |
| 加一层 service | 该逻辑同时被 ≥ 2 个入口调用（命令窗 + 托盘） |
| 引入状态管理库 | 跨窗口共享状态已经超过 3 处 |
| 引入 UI 组件库 | 自己写的基础组件超过 10 个且开始重复 |

**反模式（看到就打回）**：

- 为了"以后可能扩展"而预留的抽象层
- `utils.rs` / `helpers.ts` 这种无主题的垃圾桶
- 循环依赖靠"延迟 import"绕过
- 一个文件超过 400 行还没有拆分理由
- 在 UI 层做业务判断（如"这首歌能不能播"应在 core/sources 判定）

## 9. 目录的"三条禁令"

1. **不允许根目录堆文件**：根目录只放 `README`、`AGENTS`、`CHANGELOG`、workspace 配置和 `docs/`、`crates/`、`apps/`、`assets/`、`scripts/`、`.github/`。
2. **不允许 `misc/`、`temp/`、`test2/`**：临时文件进 `.gitignore` 的 `tmp/`，且 `tmp/` 不入库。
3. **不允许把文档放进代码目录**：所有文档在 `docs/`，代码目录里的 `README.md` 只允许写"这个 crate 干什么、入口在哪"（≤ 30 行）。
