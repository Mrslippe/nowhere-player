# ADR-0008 B站直播音频与弹幕发送

> 状态：**已接受**（2026-11-17）。B1 真机：room 23197314，3 秒内 `LIVE`、5 分钟存活、Esc 停止；B0.1 音频链路与真实弹幕发送均已验证。
> 关系：为 B 站直播引入例外；[`ADR-0004`](ADR-0004-在线音源适配层.md) 的点播模型继续有效。
---

## 1. 背景

用户要求：

1. 输入 B 站直播间，播放直播声音；
2. 向该直播间发送弹幕。

这不是“再接入一个音源”那么简单：

- 普通直播默认返回**音视频复用**的 FLV / HLS；`getRoomPlayInfo` 加 `only_audio=1` 可请求纯音频 FLV；
- 直播是**无限长、不可 seek** 的流，不能复用“先下载再播放”；
- 发送弹幕必须登录，需要 `SESSDATA` 与 `bili_jct`，与 ADR-0004 的“不做登录、不存 cookie”冲突。

B0 先验证音频链路，避免在错误的解码方案上继续施工。

---

## 2. B0 证据（2026-11-17）

房间 `21622811` / `23197314`，均 `live_status=1`；B0.1 固定 `only_audio=1`。

| 项 | 结果 |
|---|---|
| 协议 | `http_stream` / `flv`；`flv_flags=4`（仅音频） |
| 视频 | `video_tags=0`（服务端裁掉；JSON 仍报 `avc`） |
| 音频 | AAC-LC，AOT=2，48000 Hz，2 ch，约 128 kbps |
| 采样 | 400 个 AAC 帧 → 8.533 s PCM |
| 解码 | 409600 帧/声道，0 errors，RMS 0.020–0.062，非静音 |
| 网络 | 总计 143.6–143.7 KB；音频 tag 137.3 KB；视频 tag 0 |
| 耗时 | API 109–120 ms；connect 81–782 ms；FLV read 6650–8067 ms；decode 5–6 ms |
| 失败样本 | 房间 510 下播 → `playurl_info=null`；无效房间 99999999 → `code=60004` |

关键结论：

- HTTP-FLV 的 AAC 可以稳定解成 PCM；
- 解码不是瓶颈（5–6 ms），瓶颈是 CDN 读取节奏；
- `only_audio=1` 使 CDN 只发音频（`video_tags=0`）；但它不是官方冻结契约，JSON 仍报 `avc`，必须以 FLV tag 兜底；
- AAC 仅验证 AOT 1–4；HE-AAC（AOT 5/29）当前方案不覆盖；
- B0 是收满 400 帧后缓存解码，**不是流式解码**；B1 必须验证阻塞 MediaSource 的实时路径。
B0 原始代码与夹具在 `spikes/bili-live/`，不属于产品 workspace。
---

## 3. 选项

| 方案 | 结论 | 原因 |
|---|---|---|
| 先下载整段直播再播放 | ❌ | 直播无限长，无法等下载结束 |
| 外部 `ffmpeg` 子进程 | ❌（v1） | 破坏单二进制；用户不一定安装；进程/延迟/错误面更大 |
| HLS(ts/fmp4) | ❌（v1） | 分片刷新、3 s 级延迟、TS demux 复杂；FLV 已够用 |
| **HTTP-FLV + `only_audio=1` + 只解 AAC** | ✅ | 服务端裁掉视频，只剩约 128 kbps 音频；一条长连接、低延迟 |
| 终端内显示直播画面 | ❌（本 ADR） | 需要视频解码 + Sixel + 独立画布，另立项目 |

---

## 4. 决定

### 4.1 新 crate：`np-live`

新增 `crates/np-live/`，负责：

```text
bilibili_live   房间解析、getRoomPlayInfo(only_audio=1)、room get_info
flv_audio       HTTP-FLV 读取、FLV tag 解析、AAC/ADTS
live_source     实现 np_audio::AudioSource
auth            SESSDATA / bili_jct（仅内存）
danmaku         POST /msg/send、限流、错误映射
```

依赖方向：

```text
np-tui → np-live → np-audio
                 → np-sources（Transport）
```

不把网络、FLV、登录逻辑塞进 `np-tui` 或 `np-audio`。

### 4.2 扩展 `np-sources::Transport`

新增一个带默认实现的方法，旧假实现不受影响：

```rust
fn open_stream(&self, url: &str, headers: &[(&str, &str)])
    -> Result<Box<dyn Read + Send>>;
```

- `open_stream` 不能套 15 s 总超时；连接超时 5 s，读取不设总时限；
- `post_form` 只用于弹幕发送，B3 再加；Cookie 由调用方传入；
- `ReqwestTransport` 实现；测试注入假实现；
- 不启用 reqwest cookie jar，避免隐式持久化。

### 4.3 扩展 `np-audio`

- 新增 `Player::open_source(Box<dyn AudioSource>)`；
- `AudioSource` 增加 `is_seekable()`，默认 `true`；
- 直播返回 `duration_ms = None`、`is_seekable = false`；
- `Player::seek` 对直播返回明确错误，不进入 seek 握手；
- 直播结束不自动下一首，由 TUI 决定停止或重连；
- 新增依赖不引入新第三方 crate；`symphonia`、`reqwest` 已在 workspace。

### 4.4 播放模式

v1 直播采用**独占模式**：

- 开始直播停止当前队列播放，但**不清空队列**；
- 直播期间 `next/prev`、seek 禁用；
- `Space` 暂停/恢复，`Esc` 停止直播；
- 停止后队列仍在，用户可再播放；
- Player 条显示 `LIVE`，不显示 `00:00 / 00:00`；
- 不做“直播作为队列项”的复杂语义。

首个入口是 Controller 命令 `:live <room>`；B2 再评估正式 Live 页。

### 4.5 弹幕发送

- 凭据只从环境变量读：`NP_BILI_SESSDATA`、`NP_BILI_JCT`；
- **不写 settings.json、不写数据库、不写日志、不提交仓库**；
- 缺失时发送入口明确提示“未登录”，不静默失败；
- `POST https://api.live.bilibili.com/msg/send`，表单含 `roomid/msg/csrf/csrf_token/rnd` 等；
- v1 限制 20 个 Unicode 字符，发送间隔 ≥5 s；
- 错误码映射为可读状态：未登录、CSRF 失效、频率过快、内容被禁、等级不足；
- 自动化测试只打桩，不访问真实直播间；真实验收必须由用户手动执行。

### 4.6 明确不改

- 不改 `np-core` 的 `PlaybackState` 契约；
- 不改 SQLite schema；
- 不改 `settings.json` schema；
- 不做直播弹幕接收/渲染、礼物、SC、扫码登录、录制、视频画面；
- 不做 HLS 回退（B0 证明 FLV 够用；不够再单独立项）。

## 5. 后果与风险

**接受：**

- `only_audio=1` 时网络约 143.6 KB/8.5 s、无视频 tag；参数被忽略时退回“丢弃视频 tag”模式；
- 直播不可 seek，进度条语义与点播不同；
- Cookie 是敏感凭据，只能内存持有；环境变量在进程环境中仍可能被同用户进程读取；
- B 站接口非官方契约，风控/字段变化会导致直播或发送失效。

**主要风险：**

| 风险 | 缓解 |
|---|---|
| `only_audio` 被忽略 / FLV 变体 / HLS-only | 以实际 FLV tag 为准；保留丢弃视频兜底；v1 报错；B4 再评估 HLS |
| AAC 配置不是 LC，或带 CRC/多帧 ADTS | 明确失败，不静默降级 |
| 长时间断流 | B2 做重连与重新解析 playurl；B1 先报错停止 |
| 弹幕发送被风控/额外 cookie 拦截 | B0 手动验收；失败码原样映射，不自动重试 |
| 终端 UI 被直播状态污染 | 独占模式；停止后恢复队列状态 |
