# ADR-0012 直播缓冲高水位与启动安全垫

> 状态：**已接受**（2026-11-20）。

## 1. 背景

T-0108 后运行期控制器已经采用浏览器追帧脚本的死区/加速逻辑，但启动仍把
`live.buffer_ms` 当作填充目标：`open` 等待并裁剪到 target。

真机日志显示：

```text
started target_ms=1000 buffer_ms=1322
read_stall≈1050ms，约每秒一次
buffer 500–1700ms 锯齿
speed 0.60 ↔ 1.10
```

启动把 1.0s 固定进内容位置；控制器只能围绕 target 调速，不能把初始偏移追回来。

## 2. 决策

1. `live.buffer_ms` 语义改为**高水位/加速触发**，不是启动填充值。
2. 启动安全垫：`startup_ms = min(target, 700ms)`；`open` 等待并裁剪到 `startup_ms`。T-0115 真机后改为 **850ms**。
3. 启动后再 settle 200ms，等初始 GOP 到齐，再裁到 `startup_ms`，避免 700ms 起播后立刻被 3s 突发灌满。
4. 低缓冲阈值：`slow_start = min(600ms, target/2)`；`< slow_start` 用 0.60x。
5. 高水位不变：`>target` 1.10、`>target+1s` 1.20、`>target+2s` 1.30；无硬丢。
6. 日志打印 `startup_ms/settle_ms/target_ms/buffer_ms`，用于验证固定偏移是否下降。

## 3. 理由

- 脚本的 target 是上限，浏览器启动由浏览器决定；我们之前把 target 当成了启动填充。
- 700ms 是 1s 级网络块的折中：比 1000ms 少固定 300ms，又不至于首块就 underrun。
- target=1000 时 600ms 触发 0.6 过于频繁；500ms 阈值给死区留出 500ms，同时仍保留低速保护。

## 4. 风险

- 网络块若持续大于 700ms，启动仍可能 underrun；需要 T3 决定是否做自适应启动垫。
- 低缓冲阈值下调后，极端断流时更容易补静音；需观察 `U` 计数。
- 这不是“取消缓冲”；只是取消“启动必须填满 target”。

## 5. 验证

- target=1000 启动约 700ms；日志字段齐全。
- 运行期 500–1000ms 保持 1.0，<500ms 才 0.60。
- 真实直播 10 分钟，比较启动和稳定后的内容延迟。
