# ADR-0013 直播本地刷新裁到最新 300ms

> 状态：**已接受**（2026-11-20）。

## 1. 背景

`r` / `F5` 之前调用 `start_live`，重新请求 playurl、重连网络、重新等启动安全垫。
用户需要的是“把已经收到的旧缓冲丢掉，立刻回到最新”，而不是重连。

## 2. 决策

1. `LiveControl` 增加刷新标记；TUI 只请求，不阻塞。
2. `LiveAudioSource` 在下次 `read_frames` 时：
   - 取 `newest_pts`，阈值 `newest - 300ms`；
   - `queue.drop_below(threshold)`；
   - `WsolaTempo::reset`、`AacDecoder::reset`、清 `replay_until_pts`；
   - 记录 `event=refresh dropped=... keep_ms=300 buffer_ms=...`。
3. `TuiAudio::refresh_live`：
   - 视频宿主模式先关闭视频并恢复 TUI 音频；
   - 有 Player/Control 时本地刷新，不重连；
   - 暂停中刷新会恢复播放；
   - 准备中/重连中无 Player 时才退回 `start_live`。
4. `r` 与 F5 共用该路径。

## 3. 理由

- 网络正常时，重连是浪费；用户只想丢掉延迟。
- 启动/暂停缓存可能达到数秒，裁到 300ms 能立即回到低延迟。
- 裁剪后重置 WSOLA/解码器，避免旧重叠窗造成爆音。

## 4. 代价与边界

- 不能清空 cpal 150ms ring，刷新后最多还会播约 150ms 旧样本。
- 裁剪是跳变，可能有一次轻微断点；这是刷新语义，不是运行期自动丢帧。
- 网络已断时没有新帧，刷新无意义；会退回重连。
- 300ms 是保留值；如果队列本身不足 300ms，则保留全部。

## 5. 验证

- `r` 日志 `event=refresh`，不出现新的 `event=prepare`。
- 刷新后 buffer 约 300–500ms，播放继续。
- 暂停、视频模式、准备中三条路径分别验证。
