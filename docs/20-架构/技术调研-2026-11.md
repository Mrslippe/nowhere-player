# Nowhere Player 技术调研报告

> ⚠️ **历史文档（2026-11-13 标注）**：Tauri / WebView 选型已废弃，见 [ADR-0006](adr/ADR-0006-TUI宿主与渲染栈.md)。
> 保留它是为了记录当时的权衡与在线音源可行性证据；**不要据此选型**。

> 目标：极简双窗口桌面音乐播放器 —— 常驻的「播放器小窗」+ 按需打开的「CLI 风格配置窗」。
> 约束：Windows / macOS / Linux 三平台；本地 + 在线音源；性能优先（体积小、内存低、启动快）。
> 调研时间：2026-11。文中版本号均为调研时最新稳定版。

---

## 0. 结论先行（TL;DR）

| 层 | 推荐选型 | 一句话理由 |
|---|---|---|
| 桌面外壳 | **Tauri v2（2.12.x 稳定版）** | 系统 WebView，安装包 5–15 MB、常驻 40–80 MB；官方插件覆盖自启/单实例/更新/托盘/全局快捷键 |
| 前端 | **React 19 + TypeScript + Vite** | 两个形态差异极大的窗口，CSS 是最便宜的实现路径；xterm.js 直接给到「真终端」质感 |
| 配置窗 | **xterm.js 6 + 自研命令解释器（Rust 端）** | 你选的是「应用内伪终端」：视觉 100% CLI，但命令由自己解析，可控、可跨平台 |
| 音频引擎 | **symphonia（解码）+ cpal（输出）+ rubato（重采样）**，v1 可用 rodio 加速 | 纯 Rust、无 C 依赖、体积小；v1 不追位完美，v2 再自研 WASAPI/CoreAudio 独占后端 |
| 数据库 | **SQLite（rusqlite bundled）+ TOML 配置** | 单文件、零运维、库扫描与命令历史都够用 |
| 媒体集成 | **souvlaki**（MPRIS / SMTC / Now Playing） | 一套代码覆盖三平台媒体键与系统媒体面板 |
| 在线音源 | **v1 只做本地 + 一个可插拔 Source trait**；Spotify 建议直接砍掉 | 见第 4 节：Spotify 在自研播放器里已被 DRM 堵死，网易云 API 有法律风险 |

**最关键的三个判断：**

1. **Tauri 是「性能 vs 开发效率」的最优解，但不是「极致小」的解。** 如果你要的是 20 MB 内存，只有纯 Rust 原生 UI（Slint / egui）能做到；代价是失去 Web 生态、可能被 GPLv3 传染（Slint）、以及终端控件要自己写。
2. **在线音源是这个项目最大的不确定性，不是技术难点而是合规与稳定性难点。** 建议把「音源」做成插件式 trait，先只落地本地 + 直链 URL，不要一上来就绑死网易云。
3. **「命令」应该是你的一等公民 API，而不是 UI 的附属品。** 命令层写在 Rust core 里，xterm 窗口、未来的真 CLI、托盘菜单、甚至 MCP/HTTP 远程控制全部复用同一套命令注册表 —— 这是本项目最值得投的架构决策。

## 1. 需求约束复盘

从你的选择中提炼出的硬约束：

| 维度 | 你的选择 | 对选型的直接影响 |
|---|---|---|
| 平台 | Win / macOS / Linux | 排除 Win32 独占方案；Linux 的 WebKitGTK 与透明窗口是主要坑 |
| 音源 | 本地 + 在线流媒体 | 需要 HTTP + 流式解码 + 登录态管理；DRM 服务（Spotify）不可行 |
| CLI 形态 | 应用内伪终端 | 不需要 PTY，但需要「命令解释器 + 终端渲染」；同时保留未来真 CLI 的可能 |
| 技术背景 | Rust / TS / Python，性能优先 | Rust 做 core 无学习成本；TS 做 UI 顺手 |
| 优先级 | 体积小、内存低、启动快 | Tauri 起步，Slint 作为 Plan B；拒绝 Electron |
| v1 功能 | 播放控制、播放列表/队列、美化窗口、自启/单实例/更新 | 都不涉及重型能力，可在 6–8 周内出可用版 |

**未被你选中但值得提前留口的**：歌词、全局快捷键/媒体键、音乐库扫描、EQ/可视化。其中**媒体键**建议 v1 就做（成本低、体验提升大），**音乐库扫描**建议 v1.5 做（否则「添加歌曲」只能靠路径，CLI 体验会打折）。

## 2. 桌面外壳选型

### 2.1 候选对比

| 方案 | 典型体积 | 常驻内存 | 透明/毛玻璃 | 生态 | 终端 UI 成本 | 结论 |
|---|---|---|---|---|---|---|
| **Tauri v2** | 5–15 MB | 40–80 MB | Win/macOS 好，Linux 差 | 官方插件齐全 | 低（xterm.js） | ✅ 推荐 |
| Electron | 150 MB+ | 200–400 MB | 全平台好 | 最全 | 低 | ❌ 与「性能优先」冲突 |
| Slint（纯 Rust） | 10–20 MB | 20–40 MB | 需平台代码 | 中等，GPLv3/商业双许可 | 中（文本布局要自己搭） | ⚠️ Plan B |
| egui（纯 Rust） | 8–15 MB | 20–40 MB | 需平台代码 | 大 | 中（IME 偏弱） | ⚠️ 工具型可，产品型勉强 |
| Flutter + media_kit | 40 MB+ | 80–150 MB | 好 | 大 | 中 | ❌ 体积不达标 |
| Qt/QML + libmpv | 60 MB+ | 80 MB+ | 好 | 大 | 中 | ❌ 许可与体积都不划算 |

### 2.2 为什么是 Tauri

- **体积**：官方给的优化档（`lto`、`opt-level="s"`、`strip`、`panic="abort"`、`removeUnusedCommands`）能把 release 压到 10 MB 量级（[App Size 文档](https://v2.tauri.app/concept/size/)）。同类项目 Sunder（Tauri v2 + Svelte 5 + rodio）自述「二进制约 15 MB，空闲内存约 40 MB，Electron 同类 200 MB+」（[Sunder README](https://github.com/FrogSnot/Sunder)）。
- **插件覆盖你 v1 的全部系统需求**：[autostart](https://v2.tauri.app/plugin/autostart/)、[single-instance](https://v2.tauri.app/plugin/single-instance/)、[updater](https://v2.tauri.app/plugin/updater/)、[global-shortcut](https://v2.tauri.app/plugin/global-shortcut/)、[sql](https://v2.tauri.app/plugin/sql/)、[store](https://v2.tauri.app/plugin/store/)、[window-state](https://v2.tauri.app/plugin/window-state/)，托盘是核心能力（[插件总览](https://v2.tauri.app/plugin/)）。
- **窗口定制**：`decorations: false` + `data-tauri-drag-region` + CSS 圆角是官方支持的路径（[Window Customization](https://v2.tauri.app/learn/window-customization/)）。
- **版本现状**：`tauri` 稳定版 2.12.5，3.0 处于 alpha（`3.0.0-alpha.6`，2026-11 发布）—— **新项目锁 2.x，不要碰 3.0 alpha**（[crates.io](https://crates.io/crates/tauri)）。
- **可参考的真实项目密度高**：psysonic、Sunder、Nuclear（已迁到 Tauri）、qbz 1.x 都是 Tauri，出问题容易找到同类实现。

### 2.3 Tauri 的三个真实代价（必须提前接受）

1. **内存地板不是 20 MB。** WebView2 进程本身就要 30–60 MB。想要 40 MB 以内，只能换纯原生 UI。
2. **Linux 的透明/毛玻璃基本不可用。** `window-vibrancy` 官方文档明确写「**Linux: Unsupported**，模糊效果由用户系统合成器决定」（[docs.rs](https://docs.rs/window-vibrancy/latest/window_vibrancy/)）。Linux 上必须准备「不透明降级主题」。
3. **三平台 WebView 不是同一个浏览器。** Windows=WebView2(Chromium)、macOS=WKWebView、Linux=WebKitGTK，版本差异巨大（[Webview Versions](https://v2.tauri.app/reference/webview-versions/)）。CSS 要用保守子集，`backdrop-filter`、`mask`、部分 `:has()` 在 WebKitGTK 上要实测。

## 3. 音频引擎选型

### 3.1 能力矩阵

| 方案 | 格式覆盖 | 位完美/独占 | 体积 | 许可 | 适用 |
|---|---|---|---|---|---|
| **symphonia + cpal** | MP3/FLAC/AAC/ALAC/Vorbis/WAV/AIFF/ADPCM（[0.6.1 支持表](https://docs.rs/symphonia/latest/symphonia/)） | 需自己实现 | 极小 | MPL-2.0 | ✅ 首选 |
| rodio | 同上（封装 symphonia + cpal） | 否 | 小 | MIT/Apache | ✅ v1 加速 |
| libmpv | 几乎全部（含 DSD/APE/WavPack） | 可（`audio-exclusive`） | +30–40 MB DLL | GPL/LGPL | ⚠️ 需要发烧格式时 |
| FFmpeg 绑定 | 几乎全部 | 否 | +20 MB | LGPL/GPL | ⚠️ 同上 |
| GStreamer | 取决于插件 | 部分 | 依赖系统 | LGPL | ❌ 跨平台分发痛苦 |
| librespot | Spotify | 否 | 中 | MIT | ❌ 见 4.1 |

### 3.2 关键结论

- **v1 用 rodio 起步完全够**：它已经把 symphonia 解码 + cpal 输出 + 音量/暂停/seek 包好了，psysonic 就是用它做出了 gapless、crossfade、10 段 EQ（[psysonic README](https://github.com/Psychotoxical/psysonic)）。注意 rodio 正在重写内核（0.22.x），API 会有破坏性变更，**务必锁小版本**。
- **cpal 没有 WASAPI 独占模式 API**。社区从 2019 年就在要（[issue #459](https://github.com/RustAudio/cpal/issues/459)），至今没有稳定接口。真要做独占/位完美，得像 QBZ 那样自研后端：Windows 走 `windows` crate 调 IAudioClient（`AUDCLNT_SHAREMODE_EXCLUSIVE`），macOS 走 CoreAudio Hog Mode，Linux 走 ALSA `hw:` 或 PipeWire（[QBZ 技术栈](https://github.com/vicrodh/qbz)）。
- **浏览器/WebAudio 路线做不了 HiFi**。QBZ 给出的理由很直接：浏览器输出的采样率被钳制并重采样，拿不到原始 24bit/192kHz。这也是「音频必须在 Rust 侧、不能用 `<audio>` 标签」的根本原因——**你的播放器小窗只能是控制面，不能是播放面**。
- **重采样用 `rubato`**：设备采样率与曲目不一致时（44.1k 曲库 + 48k 声卡）必须有高质量重采样，否则会有可闻失真。
- **元数据/封面用 `lofty`**：Rust 生态最完整的标签库（ID3v2/FLAC/MP4/OGG/APE/WavPack + 内嵌封面），比 symphonia 的 metadata 模块覆盖面广。
- **在线流式播放**：`reqwest` 拉流 → `symphonia` 的 `MediaSourceStream` 支持非 seekable 源，但**必须自己做环形缓冲 + 预读**，否则弱网会卡；同时要处理 `Content-Type` 与容器嗅探（很多接口返回 `audio/mpeg` 但实际是 m4a）。

### 3.3 建议的音频线程模型

```
UI/命令线程 ──▶ PlayerActor(有状态, 单线程) ──▶ DecoderWorker(阻塞IO) ──▶ RingBuffer ──▶ cpal callback
                     ▲                                                          │
                     └──────────── 事件: Position/TrackEnded/Error ◀────────────┘
```

- 音频回调里**绝不做分配、加锁、格式化字符串**。
- 位置事件 10 Hz 推给 UI 即可，不要每帧。
- 切歌用「预解码下一首 + 样本级拼接」实现 gapless；crossfade 在 mixer 层做，不要在解码层做。

## 4. 在线音源可行性（这一节决定项目边界）

### 4.1 Spotify：基本判死刑

- **官方唯一合法的内嵌播放路径是 Web Playback SDK，它依赖 EME/Widevine DRM。** 社区证据很明确：Electron 里调 SDK 直接 `requestMediaKeySystemAccess` 失败、`Failed to initialize player`（[spotify/web-playback-sdk#41](https://github.com/spotify/web-playback-sdk/issues/41)）。WebView2 与 WebKitGTK 同样不带 Widevine CDM。想走通只有 castLabs 的商业 Widevine Electron 构建，那是另一个量级的成本。
- **非官方路径 librespot 也塌了。** 其 README 顶部现在挂着警告：Spotify 改了音频密钥下发机制，**新注册账号已无法取得解密密钥**，所有版本都会 `audio key error 0 1`，且「暂无已知绕过方案」（[librespot README](https://github.com/librespot-org/librespot)）。
- **务实结论**：Spotify 只能做「遥控器」——用 Web API 控制用户已经开着的 Spotify 客户端（[spotify_player](https://github.com/aome510/spotify-player) 就是这么做的，还要求 Premium）。**建议 v1 直接不做 Spotify**，在 README 里说明原因。

### 4.2 网易云 / QQ 音乐 / B 站

| 音源 | 技术可行性 | 稳定性 | 法律风险 | 建议 |
|---|---|---|---|---|
| 网易云 | 高（weapi/eapi，需 AES+RSA 加密参数） | 中（接口频繁变） | **高**（官方已施压） | 做成可选插件，不内置凭证 |
| QQ 音乐 | 中（签名算法复杂） | 中 | 高 | 暂缓 |
| B 站 | 中高（DASH 音频流 + Referer 校验 + WBI 签名） | 中 | 中 | 可作为「视频音轨」扩展 |
| YouTube | 高（yt-dlp 解析） | 高（社区维护） | 中 | ✅ 最省事的在线源 |

**必须知道的背景**：网易云第三方 API 项目 NeteaseCloudMusicApi（3 万+ star）在 2024-01 被作者清空仓库，README 只留一句「保护版权，此仓库不再维护」（[IT之家报道](https://www.ithome.com/0/746/942.htm)）。目前活跃的是社区 fork（如 [ncm-api-enhanced](https://github.com/Catamint/ncm-api-enhanced)）。这意味着：**你依赖的是一个随时可能消失、且明确被平台方反对的接口层**。

**工程上的应对**：

1. 定义 `trait MusicSource`：`search() / resolve_stream() / get_lyrics() / get_cover()`，本地文件、直链 URL、网易云、yt-dlp 都是它的实现。
2. **v1 只实现「本地文件」+「直链 URL」**（`play https://...` 就能覆盖大量场景，配合 yt-dlp 可外挂 B 站/YouTube）。
3. 在线源做成**运行时插件/可选 feature**，不进主二进制；凭证由用户自己填（cookie/token），仓库不存任何 key。
4. README 明确免责声明 + 只做「个人使用的客户端」，不分发内容。

## 5. CLI 配置窗的实现方案

### 5.1 三种形态，你该选哪种

| 方案 | 做法 | 优点 | 缺点 | 建议 |
|---|---|---|---|---|
| A. xterm.js + 自研解释器 | 前端渲染终端，命令在 Rust 解析 | 视觉最真、IME/CJK 原生支持、可控 | 要自己写行编辑/补全 | ✅ **v1 选它** |
| B. 自绘终端（div + ANSI→span） | 纯 CSS 复刻 | 体积最小、样式完全可控 | 滚动/选区/光标要自己实现 | 备选 |
| C. PTY + ratatui（真 TUI 塞进窗口） | `portable-pty` 起 TUI，xterm.js 显示 | 同一套 UI 也能跑在真终端 | 中文输入法经 PTY 体验差、复制粘贴/无障碍难 | v2 可选 |

**为什么 A 最优**：xterm.js 6.0 零依赖、MIT、原生支持 CJK 与 IME、自带 WebGL 渲染器（[npm](https://www.npmjs.com/package/@xterm/xterm)）。你这个场景 90% 的「终端感」来自等宽字体、光标、ANSI 颜色和滚动回看，xterm.js 全都免费给你；而命令解析放在 Rust 侧，才能和播放器状态共享同一份真值。

> 方案 C 的诱惑很大（等于顺手白送一个真 CLI），但**中文输入法在 PTY 里是硬伤**——用户搜「周杰伦」时会崩溃。如果未来要做，建议只用于「只读日志/诊断」子窗口。

### 5.2 命令层架构（本项目最值得设计的部分）

```
┌─────────────────────────────────────────────────────────┐
│ core::command                                            │
│  ├─ Command      : 结构化动作（serde，可序列化）          │
│  ├─ Spec         : name / aliases / args / help / complete│
│  ├─ Registry     : HashMap<&str, Spec> + 模糊匹配         │
│  └─ Response     : { lines: Vec<Line{spans, style}> }     │
└─────────────────────────────────────────────────────────┘
        ▲                    ▲                      ▲
        │                    │                      │
   xterm 窗口          IPC(local socket)        托盘/快捷键
   (TS 行编辑器)        → 未来真 CLI           → 直接发 Command
```

**语法建议**（借鉴 MPD 的动词体系 + git 的子命令）：

```bash
play                      # 继续播放
play 3                    # 播放队列第 3 首
play ./music/xxx.flac     # 播放指定文件
queue add <path|url>...   # 入队（支持通配符）
queue list --json
next / prev / pause / stop
seek +15 / seek 1:30
vol 60 / vol +5
shuffle on / repeat one
search 周杰伦              # 返回带序号的结果，后续用 play 3 引用
config set theme gruvbox
config get audio.device
source login netease
library scan ~/Music
```

**关键设计点**：

- **命令即 API**：同一个 `Registry` 通过本地 socket 暴露（Windows 命名管道 / Unix domain socket），未来 `nowhere-cli play` 就能用，等于白送一个 MPD 式的可脚本化接口。这正是 [spotify_player](https://github.com/aome510/spotify-player) 的做法（CLI 子命令通过 `client_port` 8080 与运行中的实例通信）。
- **输出结构化**：内部返回 `Vec<Line>`，渲染层再决定是 ANSI 还是 DOM。这样 `--json` 天然支持，也方便做单元测试。
- **补全**：注册表提供静态补全（子命令/flag），动态补全由 core 提供（文件路径、歌单名、设备名、标签值）。
- **错误信息要好**：`error: unknown command 'plya'` + `did you mean 'play'?`，这是 CLI 体验的分水岭。
- **历史与持久化**：`command_history` 存 SQLite，支持 ↑↓ 与 `Ctrl-R` 搜索；历史里不存敏感 token。

参考实现骨架：psysonic 的 [src-tauri/src/cli/](https://github.com/Psychotoxical/psysonic/tree/main/src-tauri/src/cli) 就是 `parse.rs / dispatch.rs / completions.rs / help.rs / presenters.rs` 这套切分，可以直接对照。

### 5.3 终端窗口的交互细节

- 启动时打印 banner（ASCII logo + 版本 + `help` 提示），像真 CLI。
- `Tab` 补全、`↑/↓` 历史、`Ctrl-L` 清屏、`Ctrl-C` 取消当前输入、`Ctrl-D` 关闭窗口。
- 长任务（扫描、搜索）显示进度行并原地刷新（`\r` + ANSI），不要刷屏。
- 支持 `clear`、`help <cmd>`、`version`、`quit`。
- 可选：`--json` 输出折叠成可点击的表格（xterm 里做链接比较麻烦，建议 v1 纯文本）。

## 6. 两个窗口的实现细节

### 6.1 播放器小窗

| 能力 | 实现 |
|---|---|
| 无边框 + 圆角 | `decorations:false` + CSS `border-radius` + `overflow:hidden`；Win11 可加 DWM 圆角偏好 |
| 拖拽 | `data-tauri-drag-region`（官方支持） |
| 透明/毛玻璃 | `transparent:true` + Windows `apply_acrylic/apply_mica`、macOS `apply_vibrancy`、Linux 降级纯色（[window-vibrancy](https://docs.rs/window-vibrancy/latest/window_vibrancy/)） |
| 置顶 | `alwaysOnTop:true`，设置里可切 |
| 点击穿透（沉浸模式） | `setIgnoreCursorEvents(true)` |
| 尺寸 | 默认 ~320×110，最小 260×88；`window-state` 记住位置 |
| 信息密度 | 封面缩略图 + 标题/艺人（Marquee 滚动）+ 进度条 + 三键；悬停才显示进度条 |

**注意**：透明窗口在 Linux（尤其 NVIDIA + XWayland）会出现停绘/闪烁，社区常见做法是**在 Linux 上直接改用不透明窗口**。请把「透明」做成平台能力探测后的可选增强，而不是默认值。

### 6.2 一个 WebView 还是两个？

| 方案 | 内存 | 复杂度 | 建议 |
|---|---|---|---|
| 两个 `WebviewWindow` | +30–45 MB（同进程共享浏览器进程，边际成本低于独立应用） | 低，各自独立尺寸/透明策略 | ✅ 默认 |
| 单窗口双形态（播放卡 ↔ 展开终端） | 省 30 MB+ | 窗口尺寸/透明/阴影要动态切换，动画容易抖 | 若内存目标 < 60 MB 再考虑 |

配置窗建议**懒创建、关闭时 hide 而非 destroy**，再次打开是毫秒级。

## 8. 数据与状态

```sql
-- 库
tracks(id, path, source, title, artist, album, album_artist, track_no, disc_no,
       duration_ms, sample_rate, channels, bitrate, codec, cover_id, added_at, mtime)
albums(id, name, artist, year, cover_id)
artists(id, name)
playlists(id, name, created_at, updated_at)
playlist_items(playlist_id, track_id, position)
queue(id, track_id, position, source_hint)
play_history(track_id, played_at, completed)
settings(key, value)          -- 也可用 TOML
command_history(id, input, ts)
sources(id, kind, credentials_blob, enabled)
```

- **配置用 TOML**（人可读、可手改、和 CLI 气质一致），运行时状态用 SQLite。
- **单一真值在 Rust**：UI 只是投影。所有变更走 `Command` → `PlayerActor` → 广播事件，避免前端和 core 各存一份状态导致不一致。
- **迁移**：`user_version` pragma + 手写 migration，别引重型 ORM。

## 10. 推荐架构

```
nowhereplayer/
├─ crates/
│  ├─ np-core/        # 领域模型、Command 定义、Registry、事件总线（无 UI 依赖）
│  ├─ np-audio/       # symphonia + cpal + rubato；PlayerActor；输出设备管理
│  ├─ np-library/     # 扫描、lofty 标签、SQLite、搜索
│  ├─ np-sources/     # trait MusicSource：local / url / netease(feature) / ytdlp(feature)
│  ├─ np-integration/ # souvlaki 媒体键、托盘事件、单实例、自启
│  └─ np-cli/         # 命令解析 + 补全 + 输出渲染（被 app 和未来 CLI 复用）
└─ apps/
   ├─ desktop/        # Tauri 壳：src-tauri + 两个窗口的 IPC 层（薄）
   └─ web/            # React：player 路由 + terminal 路由，共享设计 token
```

**铁律**：`src-tauri` 里只做「参数转换 + 调用 core」，不写业务。这样未来想换 Slint/egui 只重写 `apps/`，core 一行不动。

## 11. 分阶段实施计划（单人、业余投入估算）

### P0 · 骨架（3–5 天）
- Tauri v2 + Vite + React + TS 初始化；`removeUnusedCommands`、release profile 优化
- 两个窗口：player（无边框/置顶/拖拽）、terminal（普通窗）
- 托盘 + 单实例 + 自启 + 全局快捷键占位
- **验收**：双击图标 400 ms 内出小窗；`Ctrl+Shift+P` 唤出终端窗；关掉终端窗进程仍在

### P1 · 本地播放（1.5–2 周）
- `np-audio`：symphonia 解码 + cpal 输出 + rubato 重采样 + 音量/seek
- 队列模型（下一首/上一首/shuffle/repeat）+ 事件推送（10 Hz）
- 播放器小窗 UI：封面、标题跑马灯、进度条、三键
- **验收**：FLAC/MP3/AAC 连续播 1 小时不爆音、CPU < 5%、切歌 < 100 ms

### P2 · 命令层（1.5–2 周）
- `np-cli`：Command enum、Registry、tokenizer（`shlex`）、补全、帮助、错误建议
- xterm 窗口：行编辑、历史、Tab 补全、ANSI 输出、banner
- 命令：`play/pause/next/prev/seek/vol/queue/config/help/clear/quit`
- **验收**：不碰鼠标完成「加歌 → 播放 → 调音量 → 改主题」全流程

### P3 · 媒体库（1.5–2 周）
- `np-library`：目录扫描（`walkdir` + `rayon`）、lofty 标签、封面提取与缓存、增量扫描（mtime）
- `search` 命令 + 结果序号引用 + 模糊匹配（`nucleo` 或 SQLite FTS5）
- 持久化队列与播放位置
- **验收**：1 万首库首扫 < 60 s，二次启动 < 1 s

### P4 · 在线音源（2–3 周，风险最高）
- `trait MusicSource` + 本地/直链实现
- 可选：yt-dlp 集成（外部依赖，失败要优雅降级）
- 可选：网易云（登录态、搜索、直链、歌词）—— 独立 feature，默认不编译
- **验收**：网络断开时 UI 不卡死；错误信息可读；不泄漏凭证

### P5 · 打磨发布（1–2 周）
- 三平台透明/毛玻璃降级策略；Linux 不透明主题
- 更新器 + 签名；GitHub Actions 三平台产物
- 崩溃日志、`--verbose`、首次启动引导
- **验收**：Win/macOS/Ubuntu 各跑通安装 → 播放 → 更新

**总计约 8–11 周**（业余时间按 15 h/周算）。

## 13. 待你拍板的四个问题

1. **Spotify 是否直接砍掉？**（建议砍；若必须留，只能做「遥控已有客户端」）
2. **内存目标到底是 80 MB 还是 40 MB？** 前者 Tauri 稳，后者要重新考虑 Slint（且接受 GPLv3 或付费）。
3. **开源协议选什么？** 若用 Slint 就必须 GPLv3；用 Tauri 可自由选 MIT/Apache。
4. **v1 是否包含「音乐库扫描」？** 不含的话，CLI 加歌只能靠路径，体验会明显打折。
