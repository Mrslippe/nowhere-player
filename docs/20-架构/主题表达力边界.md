# 主题表达力边界与用户自定义

> 问题不是"设计一个 TUI 主题"，而是两个架构问题：
> 1. **在当前主题架构下，能做出多原汁原味的 TUI？**
> 2. **这种主题，用户能不能自己做出来？**

---

## 1. 当前架构能表达什么（准确清单）

| 层 | 内容 | 用户可改 |
|---|---|---|
| `tokens` | **14 个颜色**：bg / bgElev / bgHover / fg / fgMuted / fgFaint / accent / accentSoft / accentFg / danger / warn / success / line / lineStrong | ✅ 任意 |
| `skin` | **2 个枚举**：`plain` / `phosphor`（圆角、边框、阴影、字体、密度、出血） | ❌ 只能选 |
| 公开契约 | 12 个选择器 + 14 个颜色变量 | ✅ 名义上 |

**一句话**：用户能改**颜色**，不能改**结构**。

---

## 2. 逐条对照：原汁原味 TUI 需要什么

| TUI 要素 | tokens 能表达 | 现有 skin 能表达 | 缺什么 |
|---|---|---|---|
| 深色 / 浅色底 | ✅ | ✅ | — |
| 单一强调色 | ✅ | ✅ | — |
| 等宽字体 | ❌ | ✅ | — |
| 紧凑密度 | ❌ | ✅ | — |
| **整行反白选中** | ❌ 无 `selectionFg` | ❌ 组件只画左侧条 | 新 token + 组件分支 |
| **框线嵌标题** | ❌ | ❌ | 结构（box-drawing） |
| **字符块进度** | ❌ | ❌ | 组件渲染分支 |
| **全大写标签** | ❌ | ⚠️ 只能硬编在 skin 里 | 排版轴 |
| **斑马纹表格** | ❌ 无 stripe token | ❌ | 新 token |

**结论**：颜色层面能表达约 **60%**，结构层面接近 **0%**。
**只靠 tokens，做不出任何"原汁原味"的 TUI**——这也是第一版草案"大同小异"的根本原因。

---

## 3. 给用户开放结构能力的三条路

| 方案 | 表达力 | 成本 | 风险 |
|---|---|---|---|
| **A. 结构参数枚举**（structure 块） | 高（覆盖已知 TUI 语法） | 3–4 天 | 轴设计错了要返工 |
| B. 用户 CSS（ADR-0003 的 L2） | 无限 | 2 天 + 长期契约维护 | 布局可被写坏；升级即碎 |
| C. 每个 TUI 变体做成内置 skin | 高 | 每个 1–2 天，不可组合 | 用户无法自己扩展 |

**推荐 A**，理由：

- B 的表达力是"能改一切"，但**用户要的是"做出好看的 TUI"，不是"能写 CSS"**；
- C 把成本转嫁给我们，且用户永远只能等我们发版；
- A 是"给乐高块，不给刀"——**枚举轴保证结果一定成立**。

---

## 4. 推荐的 structure 轴（8 个）

```jsonc
"structure": {
  "radius":    "none | subtle | soft",        // 0 / 2px / 6px
  "border":    "none | hairline | box",       // 无 / 1px 高光 / 1px 实线框
  "density":   "compact | normal | relaxed",  // 行高 20 / 24 / 28
  "progress":  "line | blocks | bracket",     // 细线 / ▰▱ / [■■□□]
  "selection": "bar | reverse | bg",          // 左条 / 整行反白 / 仅底色
  "labels":    "sentence | upper",            // 原样 / 全大写+字距
  "stripe":    "off | on",                    // 表格斑马纹
  "font":      "mixed | mono"                 // 界面无衬线 / 全等宽
}
```

每个轴映射到一组 **CSS 变量 + `data-*` 属性**，**不开放任意 CSS**。

### 4.1 表达力验证：能否拼出三种 TUI

| 方向 | radius | border | selection | progress | labels | stripe |
|---|---|---|---|---|---|---|
| **T1 块面** | none | none | **reverse** | blocks | upper | on |
| **T2 线框** | none | **box** | bg | blocks | upper | off |
| **T3 票据**（亮色 token） | none | box | **reverse** | **bracket** | upper | off |

**三种都能拼出来**——说明这 8 个轴对"已知 TUI 语法"是够用的。

### 4.2 这些轴对现有两套 skin 的影响

- `plain` = radius soft、border hairline、density normal、progress line、selection bar、labels sentence、stripe off、font mixed
- `phosphor` = radius none、border none、density compact、progress line、selection bg、labels sentence、stripe off、font mono

**现有 skin 变成"结构预设"**，而不是硬编码的 CSS 文件。这是本次架构改造的核心。

## 5. 用户能不能自己做（直接回答）

| 阶段 | 用户能做什么 |
|---|---|
| **今天** | 改 14 个颜色 + 选 2 个 skin 之一 → **做不出 TUI** |
| **加了 structure 之后** | 改 14 个颜色 + 选 8 个轴 → **能做出上面三种 TUI** |
| 还缺什么 | ① 轴的校验与降级 ② 预览方式 ③ 编辑入口 |

**编辑入口现状**：`theme export <id>` 导出样例 JSON，用户改完放回 `themes/` 目录即生效——**这条路已经通了**，缺的是文档和校验。

---

## 6. 对 ADR-0003 的修订

原模型：

```
L1 tokens（开放） → L3 skin（我方，枚举）
```

新模型：

```
L1   tokens     开放            14 个颜色
L1.5 structure  开放（枚举）     8 个结构轴      ← 新增
L2   user CSS   推迟            任意样式
L3   skin       我方            结构预设 = structure 的一组取值
```

**L1.5 的位置很关键**：它比 token 表达力强，比 CSS 安全，**让"原汁原味 TUI"成为用户可达的目标，而不是我们独有**。

## 7. 成本

| 项 | 估 |
|---|---|
| 8 个轴的 CSS/组件分支 | 3 天 |
| `structure` schema + 校验 + 降级 | 1 天 |
| 三个内置 TUI 主题（验证轴够用） | 1 天 |
| 文档（主题格式 + 用户指南） | 0.5 天 |
| **合计** | **≈5.5 天** |

---

## 9. 一句话结论

> **不是"我们做一个 TUI 主题"，而是"把结构能力从 skin 里拆出来，变成用户可组合的 8 个轴"。**
> 做完之后，TUI 主题只是这套轴的第一个组合，**用户能自己做出它，也能做出我们没想到的**。
